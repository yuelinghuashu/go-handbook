# 19 测试

> Go 版本：>= 1.27.1  
> 相关标准库：testing、net/http/httptest、testing/fstest、testing/iotest

Go 把测试当成语言的一部分：测试文件、测试函数、运行命令、覆盖率、基准、模糊测试全部由标准库和 `go test` 提供，**不需要任何第三方框架**。

读完这一篇，你会知道为什么 Go 社区对"断言库"兴趣不大，以及怎么写出既能定位问题、又不会因为实现改动而碎掉的测试。

## 第一个测试

测试文件以 `_test.go` 结尾，和被测试的代码放在同一个目录、同一个包：

```text
calc/
├── calc.go
└── calc_test.go
```

```go
package calc

import "testing"

func TestAdd(t *testing.T) {
    if got := Add(1, 2); got != 3 {
        t.Errorf("Add(1,2) = %d, want 3", got)
    }
}
```

```bash
go test ./...       # 跑当前模块所有包
go test -v ./...    # 打印每个测试的名字和结果
go test -run TestAdd ./calc   # 只跑匹配的测试
```

命名规则是硬性的：

- 测试函数必须叫 `TestXxx`（`Xxx` 首字母大写），签名必须是 `func(t *testing.T)`。
- `_test.go` 文件**不参与普通构建**，所以测试依赖不会进入你的二进制。
- 测试函数名后面可以跟小写或下划线来区分场景：`TestAdd_negative`、`TestParseEmpty`。

## 报告失败

只有四个方法需要记：

| 方法 | 行为 |
| --- | --- |
| `t.Error(...)` / `t.Errorf(...)` | 标记失败，**继续执行**当前测试 |
| `t.Fatal(...)` / `t.Fatalf(...)` | 标记失败，**立即终止**当前测试（内部调 `runtime.Goexit`） |
| `t.Log(...)` / `t.Logf(...)` | 记录日志，只在 `-v` 或测试失败时输出 |
| `t.Skip(...)` | 跳过这个测试，标记为 SKIP |

选择标准很简单：

- **失败之后继续跑没有意义**就用 `Fatal`。最典型的是 `if err != nil { t.Fatal(err) }`——后面所有断言都依赖这一步成功。
- **想一次看到所有问题**就用 `Error`。表驱动测试里尤其有用：一次跑完能看到哪几行错了。

```go
func TestDiv(t *testing.T) {
    got, err := Div(6, 3)
    if err != nil {
        t.Fatal(err) // 拿不到 got，后面没法测
    }
    if got != 2 {
        t.Errorf("Div(6,3) = %d, want 2", got)
    }
}
```

**Go 没有断言库，这是刻意的。** 标准库不提供 `assert.Equal` 之类的东西，官方立场是：测试里的判断应该显式写出来，失败信息应该由你决定说什么。好处是失败消息天然带着上下文（"Div(6,3) = 3, want 2" 比 "expected 2, got 3" 有用），坏处是样板多。真要用断言，第三方库（testify 等）是常见选择，但**先写几个纯标准库的测试再决定**——很多团队最后发现不需要。

一条实用习惯：**失败消息里带上输入、实际值、期望值**。写成 `t.Errorf("Div(%d,%d) = %d, want %d", a, b, got, want)`，失败时不看代码也知道发生了什么。

## 表驱动测试

同一段逻辑要用多组输入验证时，把用例写成表：

```go
func TestDiv(t *testing.T) {
    tests := []struct {
        name    string
        a, b    int
        want    int
        wantErr error
    }{
        {"整除", 6, 3, 2, nil},
        {"不整除", 7, 2, 3, nil},
        {"除零", 1, 0, 0, ErrDivZero},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            got, err := Div(tt.a, tt.b)
            if !errors.Is(err, tt.wantErr) {
                t.Fatalf("Div(%d,%d) err = %v, want %v", tt.a, tt.b, err, tt.wantErr)
            }
            if got != tt.want {
                t.Errorf("Div(%d,%d) = %d, want %d", tt.a, tt.b, got, tt.want)
            }
        })
    }
}
```

要点：

- **`name` 字段不要省**。它让失败信息变成 `TestDiv/除零`，一眼知道是哪个用例。
- **加新用例只需要加一行**，这是表驱动最大的价值：覆盖率的提升不增加代码复杂度。
- 断言差错的写法是 `errors.Is(err, tt.wantErr)` 而不是 `err == tt.wantErr`，这样包装过的错误也能匹配（见 `05-错误处理.md`）。
- 循环变量的捕获问题从 Go 1.22 起已经不存在（见 `03-控制流.md`），不需要再写 `tt := tt`。

## 子测试与并行

`t.Run` 产生的是**真正的子测试**：可以单独运行、可以并行、失败信息带层级：

```bash
go test -run 'TestDiv/除零' ./calc   # 只跑一个子测试
```

实测输出层级：

```text
=== RUN   TestDiv
=== RUN   TestDiv/整除
=== RUN   TestDiv/不整除
=== RUN   TestDiv/除零
--- PASS: TestDiv (0.00s)
    --- PASS: TestDiv/整除 (0.00s)
```

加 `t.Parallel()` 就让子测试并行执行：

```go
for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
        t.Parallel() // 这个子测试会和其他并行的子测试一起跑
        // ...
    })
}
```

`t.Parallel()` 的语义要理解清楚，否则会写出假的并行：

- 调用 `t.Parallel()` 会**先暂停当前测试**，把它交还给父测试；父测试的所有子测试都暂停后，它们才一起恢复并行执行。
- 并行度由 `-parallel n` 控制，默认等于 `GOMAXPROCS`。
- **只能对局部变量做断言**。并行测试里访问共享的全局状态就是数据竞争，`go test -race` 会抓出来。

实测两个各自 `time.Sleep(50ms)` 的并行测试，总耗时约 0.05s，确实是并行跑的。

**什么时候不该并行**：测试里有共享的可变状态（全局变量、环境变量、临时文件名的固定路径）、或者本来就依赖执行顺序时。`t.Setenv` 与 `t.Parallel` **不能同时用**，用了会直接 panic（实测 Go 1.27.1）：

```text
panic: testing: test using t.Setenv, t.Chdir, or cryptotest.SetGlobalRandom can not use t.Parallel
```

原因是环境变量和当前工作目录都是**进程级**的，并行测试会互相踩。

## 测试辅助

### t.Helper：让失败指向调用者

封装断言辅助函数时**必须**加 `t.Helper()`，否则失败信息会指向辅助函数内部，而不是出问题的调用点。对比实测：

```go
func noHelper(t *testing.T, got, want int) {
    if got != want {
        t.Errorf("got %d want %d", got, want) // 报错指向这一行（辅助函数里）
    }
}

func withHelper(t *testing.T, got, want int) {
    t.Helper() // 报错指向调用 withHelper 的那一行
    if got != want {
        t.Errorf("got %d want %d", got, want)
    }
}
```

```text
--- FAIL: TestNoHelper (0.00s)
    helper_test.go:7: got 1 want 2      ← 指向辅助函数内部，没用
--- FAIL: TestWithHelper (0.00s)
    helper_test.go:19: got 1 want 2     ← 指向真正的调用点，有用
```

### t.Cleanup：测试结束时的清理

`t.Cleanup(f)` 注册的函数在本测试（含子测试）结束时执行，**顺序是后进先出**：

```go
func TestCleanupOrder(t *testing.T) {
    t.Cleanup(func() { t.Log("cleanup 1") })
    t.Cleanup(func() { t.Log("cleanup 2") })
    t.Log("body")
}
```

```text
    calc_test.go:43: body
    calc_test.go:42: cleanup 2
    calc_test.go:41: cleanup 1
```

和 `defer` 的区别：`defer` 属于**当前函数**，`t.Cleanup` 属于**整个测试**。所以清理逻辑写在辅助函数里时，应该用 `t.Cleanup`——用 `defer` 会在辅助函数返回时就执行，往往太早。多个辅助函数各自注册清理也能保证按注册的逆序执行。

### t.TempDir：自动清理的临时目录

```go
func TestWrite(t *testing.T) {
    dir := t.TempDir() // 每个测试一个独立目录，测试结束后自动删除
    path := filepath.Join(dir, "a.txt")

    if err := os.WriteFile(path, []byte("x"), 0o644); err != nil {
        t.Fatal(err)
    }
}
```

不要用 `os.MkdirTemp` + 手动删除：失败提前 return 时清理就漏了，而 `t.TempDir` 由测试框架兜底。并行测试里用 `t.TempDir` 也天然安全，因为每个测试拿到的是不同目录。

### t.Setenv / t.Chdir

```go
func TestConfig(t *testing.T) {
    t.Setenv("APP_ENV", "test") // 测试结束后自动恢复原值
    // 且这个测试会被强制串行执行
}
```

`t.Setenv` 会**自动恢复**原值，所以不需要自己 `defer os.Setenv(...)`；它同时禁止该测试调用 `t.Parallel()`。需要切工作目录时用 `t.Chdir(dir)`（Go 1.24 起），同样会自动恢复。

### t.Context 与 t.Deadline：把测试的生命周期传进去

`t.Context()`（Go 1.24 起）返回一个**在 Cleanup 函数执行之前就被取消**的 context。它的用处是"被测代码需要 context"这类接口——后台 goroutine、连接池、HTTP 客户端，都能跟着测试结束一起收尾，不用自己造一个 `context.Background()` 再手动取消（`testing.go` 的顺序是：先 `cancelCtx()`，再跑 `t.Cleanup` 注册的函数）：

下面这个例子用到 goroutine、channel 和 `context`，它们分别在 `39-并发基础.md` 和 `40-context.md` 讲；这里只要理解"测试一结束，ctx 就被取消，后台活跟着收尾"。

```go
// 写在 func TestWorkerStops(t *testing.T) { ... } 里
ctx := t.Context()

done := make(chan struct{})
go func() {
    defer close(done)
    <-ctx.Done()
}()

t.Cleanup(func() { <-done }) // Cleanup 里 ctx 已经取消，这里等得到
```

有个反直觉的后果：**`srv.Shutdown(t.Context())` 写在 `t.Cleanup` 里等于没等优雅关闭**。`t.Context()` 正是在 Cleanup 之前被取消的，`Shutdown` 拿到已取消的 context 会立刻返回 `context.Canceled`，在途请求根本不会被等。Cleanup 里想立刻收掉就用 `srv.Close()`；真要优雅关闭，就现造一个 `context.WithTimeout(context.Background(), 5*time.Second)`——完整写法见 `31-网络与HTTP.md` 的"优雅关闭"一节。

另外 `t.Context()` **没有截止时间**，它只保证"测试结束时取消"。想要 `-timeout` 对应的截止时间，用 `t.Deadline()`——它返回绝对时间与 `ok`（`ok == false` 表示没设超时，即 `-timeout=0`）：

```go
func TestWithDeadline(t *testing.T) {
    d, ok := t.Deadline()
    if !ok {
        t.Skip("没有设置 -timeout，测试不限时")
    }

    // 把测试超时传给被测代码，留一点余量给失败信息的输出
    ctx, cancel := context.WithDeadline(context.Background(), d.Add(-time.Second))
    defer cancel()

    _ = ctx
}
```

`ok` 为 `false` 只有一种情况：`-timeout=0`（测试不限时），所以 `if ok` 和 `if !ok { t.Skip(...) }` 两种写法都要照顾到——别默认 `d` 一定可用，把判断写进代码比记住默认值可靠。

上面两段都依赖真实的 `*testing.T`，`tools/checkdocs` 只能把它们包成 `func main()` 跑（那时 `t` 是零值，`t.Deadline()` 必然返回 `ok == false`），所以这两段没有写 `// 期望输出`；它们的语义由 `examples/concurrency_test.go` 里的 `TestContextCanceledBeforeCleanup` 与 `TestDeadlineIsInTheFuture` 兜住。

### testing.Short：区分快慢测试

```go
func TestSlow(t *testing.T) {
    if testing.Short() {
        t.Skip("short 模式跳过")
    }
    // 耗时的集成测试
}
```

```bash
go test -short ./...   # 跳过慢测试
```

约定是：**单元测试要能在 `-short` 下秒级跑完**，需要网络、外部服务、大量数据的测试放到 `-short` 之外，或者用构建约束隔离。

## 基准测试

基准函数叫 `BenchmarkXxx`，签名是 `func(b *testing.B)`：

```go
func BenchmarkSum(b *testing.B) {
    nums := make([]int, 1000)
    for i := range nums {
        nums[i] = i
    }

    b.ReportAllocs()
    for b.Loop() { // Go 1.24 起的标准写法
        Sum(nums)
    }
}
```

```bash
go test -run '^$' -bench . -benchmem ./...
```

```text
BenchmarkSum-12    	 2577158	       471.2 ns/op	       0 B/op	       0 allocs/op
```

- **`-run '^$'`** 表示不跑任何普通测试，只跑基准——否则测试的耗时也会算进来。
- **`for b.Loop()`** 是 Go 1.24 起的写法，取代了老式的 `for i := 0; i < b.N; i++`。它更不容易出错：编译器**不会优化掉**循环体里的调用（老写法里如果结果没被使用，整个循环可能被优化没），并且自动处理计时器的启停。
- `b.ReportAllocs()` 或 `-benchmem` 会输出每次操作的内存分配，这是最有价值的两列：**`allocs/op` 是否为 0，通常比 `ns/op` 更值得关注**（见 `10-指针.md` 的逃逸分析）。
- 结果里的 `-12` 是 `GOMAXPROCS`。
- 比较两组基准不要靠肉眼看 `ns/op`，用 `golang.org/x/perf/cmd/benchstat` 的 `benchstat old.txt new.txt`，它会给出统计显著性。

写基准的两个常见错误：**setup 放进了循环**（把准备数据的代码写在 `b.Loop()` 内部，测的是准备数据的耗时），以及**结果被优化掉**（这也是 `b.Loop()` 要解决的问题之一——它保证循环体不会被消除）。

## 示例函数

`ExampleXxx` 是**会被执行的文档**：函数体里的输出必须和 `// Output:` 注释完全一致，否则测试失败。

```go
func ExampleAdd() {
    fmt.Println(Add(1, 2))
    // Output: 3
}
```

```go
func ExampleDiv() {
    v, err := Div(6, 3)
    fmt.Println(v, err)

    v, err = Div(1, 0)
    fmt.Println(v, err)
    // Output:
    // 2 <nil>
    // 0 division by zero
}
```

- 输出顺序不确定时用 `// Unordered output:`。
- **没有 `// Output:` 注释的 `Example` 不会被执行**，但会出现在 `go doc` 里，所以"只想展示、不想断言"也是合法用法。
- 命名决定它挂在哪儿：`ExampleAdd` 挂在函数 `Add` 上，`ExampleUser_Name` 挂在 `User` 类型的方法上。
- 这是**文档与实现保持同步的机制**，比在注释里手写输出可靠得多。本系列文档里的示例输出如果有问题，正确做法就是把它们变成 `Example` 函数。

## 模糊测试

Fuzz 函数叫 `FuzzXxx`，签名是 `func(f *testing.F)`（Go 1.18 起）：

```go
func FuzzDiv(f *testing.F) {
    f.Add(6, 3)   // 种子语料：作为普通测试跑时用它
    f.Add(0, 1)

    f.Fuzz(func(t *testing.T, a, b int) {
        got, err := Div(a, b)

        // 先处理"这个输入必须返回错误"的分支，再看不变量
        if b == 0 {
            if err == nil {
                t.Fatalf("Div(%d, 0) 应返回错误，实际返回了 %d", a, got)
            }
            return
        }
        if err != nil {
            t.Fatalf("Div(%d, %d) 返回了意外错误：%v", a, b, err)
        }

        // 到这里 b != 0 且没有错误，断言你关心的那些不变量
        if got*b != a-a%b {
            t.Fatalf("Div(%d, %d) = %d，乘法验算不回去", a, b, got)
        }
    })
}
```

顺序不是随便排的，两点值得记住：

- **先写"必须出错"的分支，再写"不该出错"的分支**。反过来写（先 `if err != nil { return }`、再判 `b == 0`）其实**也能抓到**"除零没报错"的 bug：坏实现返回 `nil` 时不会命中那条 `return`，后面那句 `t.Fatalf` 照样会触发。但它的失败信息写不出有用的话——"b == 0 时不应返回 nil error"在 `err == nil` 已经成立时读起来是自相矛盾的，而被测实现的合约（除零返回错误）也不该藏在一条守卫语句后面。按输入的性质分支，代码和失败信息都直说结论。
- **不变量本身也可能踩到语言的坑**。验算除法很自然会写成"商 × 除数 + 余数 == 被除数"，但它在 `a == math.MinInt, b == -1` 时会**溢出**——这个除法的结果已经超出 `int` 范围，Go 规定此处回绕成 `MinInt`，于是加法一算就错，一个正确的实现反而被报成 bug。上面写成 `got*b == a-a%b`：等价，而且右边的量级足够小、不会溢出。模糊测试的另一半价值就在这里：它会把你随手写的不变量也放到极端输入上试一遍。

两种运行方式：

```bash
go test -run FuzzDiv ./...          # 只跑种子语料，和普通测试一样快
go test -fuzz FuzzDiv -fuzztime 3s ./...   # 真正开始模糊测试
```

实测 `-fuzztime 3s` 的输出：

```text
fuzz: elapsed: 0s, gathering baseline coverage: 2/2 completed, now fuzzing with 12 workers
fuzz: elapsed: 3s, execs: 1026154 (341774/sec), new interesting: 2 (total: 4)
PASS
```

要点：

- **`f.Add` 的种子语料必须永远通过**，所以日常 `go test ./...` 会顺带跑这些用例，模糊测试不会成为"只有专门跑才有用"的死代码。
- **失败的输入会被自动保存**到 `testdata/fuzz/FuzzXxx/` 下，之后 `go test` 会用它做回归。这就是模糊测试最有价值的产物——**一个最小化的、真实的崩溃用例**。
- `-fuzz` 只能指定一个目标（一次盯一个函数），`-fuzztime` 限制时长，不写会一直跑。
- 布尔/字符串/整数/浮点/字节切片都能作为 `f.Fuzz` 的参数类型，不支持结构体和切片等复合类型——需要的话先拆成基本类型。
- 最适合模糊测试的是**解析器**：JSON、URL、协议、配置、正则。这类代码的输入空间大、边界条件多，人想不到的用例它都能找到。

## 覆盖率

```bash
go test -cover ./...                          # 每个包的覆盖率
go test -coverprofile=cover.out ./...          # 生成覆盖率数据
go tool cover -func=cover.out                  # 按函数列出
go tool cover -html=cover.out                  # 生成 HTML，浏览器里逐行看
```

```text
testch/calc.go:11:	Div		100.0%
testch/calc.go:19:	Sum		100.0%
total:			(statements)	100.0%
```

- **`-cover` 统计的是语句覆盖率**，它只说明"这行被执行过"，不说明"判断对了"。100% 不代表没 bug，60% 基本说明有功能没测。
- `-covermode` 三档：`set`（默认，是否执行过）、`count`（执行次数）、`atomic`（计数且并发安全，跑 `-race` 或并行测试时用这个）。
- **别把覆盖率当 KPI**。覆盖率的价值在于**找出完全没被碰过的分支**，而不是把数字刷到某个阈值。对错误处理分支尤其有用——很多 `if err != nil` 里的逻辑从来没被执行过。
- 想统计跨包的整体覆盖率（一个包的测试顺带覆盖了另一个包），加 `-coverpkg=./...`。

## 常用 flag 与缓存

| flag | 作用 |
| --- | --- |
| `-run regexp` | 只跑匹配的测试（对子测试用 `TestDiv/除零` 这样的路径匹配） |
| `-bench regexp` | 只跑匹配的基准 |
| `-v` | 输出每个测试的名字和 `t.Log` |
| `-count n` | 每个测试重复跑 n 次；**`-count=1` 用来绕过结果缓存** |
| `-short` | 置 `testing.Short()` 为 true |
| `-timeout d` | 超时时间，默认 10m，超时会打印所有 goroutine 的调用栈 |
| `-race` | 开启数据竞争检测（见 `39-并发基础.md`） |
| `-failfast` | 第一个失败就停 |
| `-shuffle on` | 打乱测试执行顺序，用来抓"测试之间互相依赖"的隐藏问题 |
| `-json` | 输出机器可读的事件流，IDE 和 CI 用它 |

**结果缓存**：`go test` 会缓存**成功**的结果（按源码、依赖、环境、命令行等 factors 计算），所以重复跑同一批测试会瞬间返回，输出里带 `(cached)`：

```text
$ go test ./...
ok  	testch	0.054s
$ go test ./...
ok  	testch	(cached)     ← 直接复用上次结果
$ go test -count=1 ./...
ok  	testch	0.054s       ← 强制重跑
```

改了代码、改了环境变量、或者换了 flag 都会自动失效。失败的结果**不缓存**，所以调试时不用担心。

## TestMain

需要在整个包的测试前后做全局准备/清理时，用 `TestMain`：

```go
func TestMain(m *testing.M) {
    setup()             // 例如启动测试用的数据库容器
    code := m.Run()     // 跑本包所有测试
    teardown()
    os.Exit(code)       // 必须显式退出，且要传 m.Run 的返回值
}
```

三条注意：

- 一个包**最多一个** `TestMain`。
- 一定要 `os.Exit(code)`：不调用会导致"测试跑完但进程不退"或者退出码错误，CI 就判断不出成功失败。
- 加了 `TestMain` 之后，**`m.Run()` 之前不能有任何 `t`**：这里没有可用的 `*testing.T`。

实测输出（`TestMain` 的 `fmt.Println` 会出现在测试输出里）：

```text
TestMain: 全局 setup
--- PASS: TestSlow (0.00s)
PASS
TestMain: 全局 teardown
ok  	testch	0.053s
```

它能做的事，很多场景其实用 `t.Cleanup` 或 `sync.Once` 更合适；`TestMain` 适合"真的需要整个包只做一次、且必须包住所有测试"的场景。

## 测试替身

Go 的测试替身主要靠**接口 + 手写假实现**，而不是 mock 框架：

```go
type Store interface {
    Get(id string) (string, error)
}

// 假实现：行为完全由测试决定
type fakeStore struct {
    data map[string]string
    err  error
}

func (f fakeStore) Get(id string) (string, error) {
    if f.err != nil {
        return "", f.err
    }
    return f.data[id], nil
}
```

这样被测代码接受 `Store` 接口，测试传 `fakeStore` 进去——**不需要生成代码，也不需要框架**。接口定义在使用方（见 `18-包与工程组织.md`）这条设计建议，主要动机就是让替换变简单。

标准的假实现工具（都在标准库里）：

- **`net/http/httptest`**：测 HTTP handler 不需要真的起端口：

  ```go
  rec := httptest.NewRecorder()
  req := httptest.NewRequest("GET", "/sum", nil)

  Handler().ServeHTTP(rec, req)

  if rec.Code != http.StatusOK {
      t.Fatalf("status = %d, want 200", rec.Code)
  }
  fmt.Println(rec.Body.String()) // {"sum":6}
  ```

  `httptest.NewServer` 则起一个真的本地服务器，适合测客户端（返回的 `*httptest.Server` 要 `defer s.Close()`）。

- **`testing/fstest`**：`fstest.MapFS` 用内存里的 map 当文件系统，测接受 `fs.FS` 的代码很方便：

  ```go
  fsys := fstest.MapFS{
      "config/app.json": &fstest.MapFile{Data: []byte(`{"a":1}`)},
  }
  b, err := fsys.ReadFile("config/app.json")
  ```

- **`testing/iotest`**：提供"每次只读 1 字节"、“读到一半就报错”这类**故意制造麻烦**的 Reader，专门用来测你的代码有没有正确处理短读和错误。

- **`strings.NewReader` / `bytes.Buffer` / `bytes.NewReader`**：最简单的假 IO。任何接受 `io.Reader` 的代码都能用一个字符串喂进去（见 `21-io与流.md`）。

- **`os.DirFS(t.TempDir())`**：需要真实文件系统语义（权限、目录遍历）时，用临时目录当根。

## 测试的组织

### 包内测试 vs 外部测试包

同一个目录下可以有两种测试包：

```go
package calc      // 包内测试：能访问未导出标识符
```

```go
package calc_test // 外部测试包：只能访问导出的 API，需要 import "xxx/calc"
```

选择标准：

- 需要测**未导出**的函数、或者需要构造内部状态时，用包内测试。
- 想**从使用者视角**验证公开 API 时，用外部测试包——它天然阻止你依赖实现细节。大型项目常见做法是两者并用，文件名区分：`calc_internal_test.go` / `calc_test.go`。

### testdata 目录

名字叫 `testdata` 的目录**会被构建工具忽略**，不会被当成包，是放测试固件的标准位置：

```text
calc/
├── testdata/
│   └── sample.json
└── calc_test.go
```

实测 `go list ./...` 只列出 `calc`，不会把 `testdata` 当包。读它用相对路径 `testdata/sample.json`（测试的工作目录就是包目录）。

## 实践建议

- **测试的失败消息要能独立定位问题**：带上输入、实际值、期望值。
- **一个测试只验证一件事**，名字说清验证的是什么。"测试一切"的大函数失败时你只知道"坏了"。
- **优先表驱动**：加用例的成本越低，用例越多。
- **不要断言实现细节**。测"输出是什么"而不是"内部调用了谁几次"——后者会让任何重构都变成改测试。
- **测试要能重复跑**：不依赖执行顺序、不依赖外部网络、不依赖当前时间（要测时间相关逻辑用 `testing/synctest`，见 `42-并发模式与运行时行为.md`）。
- **把文档里的输出变成 `Example`**：这样文档和代码不会各说各话。
- **解析类代码加 `Fuzz`**：投入产出比最高的一类模糊测试。
- **`-race` 和 `-count=1` 进 CI**：前者抓并发问题，后者防止误信缓存。CI 上再加一个 `-shuffle on`，顺序依赖的问题会自己浮出来。
- **先写测试再修 bug**：把复现 bug 的用例写成测试，修完它就跑得过，这样修复不会被后续改动悄悄破坏。
