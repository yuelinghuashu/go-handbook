# 18 包与工程组织

> Go 版本：>= 1.27.1  
> 相关标准库：runtime（只用 `runtime.GOOS` / `runtime.GOARCH` 判断运行平台）

读这一篇不需要新的语言特性，但需要先熟悉函数（`04-函数.md`）、结构体（`09-struct.md`）和接口（`12-接口.md`）。

## 包与包名

Go 的组织单位是**包**，不是文件。一个目录里的所有 `.go` 文件（不含 `_test.go`）属于同一个包，它们之间可以直接访问彼此的东西，不需要导入。

每个文件开头声明自己属于哪个包：

```go
package user
```

三条约定：

- **一个目录 = 一个包**。同一个目录下的文件必须用同一个包名；反过来，同一个包不能跨目录。
- **包名用小写、简短、单词**，不要用下划线或驼峰：`user`、`http`、`strconv`，而不是 `userService`、`user_service`。
- **包名不必等于目录名**，但强烈建议相等。目录 `user/` 里写 `package account` 是合法的，但导入的人必须写 `import "example.com/user"` 却用 `account.X` 访问——除了历史包袱（如 `gopkg.in/yaml.v2` 的包名是 `yaml`），不要这么做。

`package main` 是特殊的：它编译成可执行文件，必须有一个 `main` 函数作为入口。库代码不要用 `package main`。

### internal：只给本模块用

把包放在名为 `internal` 的目录下，它就**只能被以该 `internal` 目录的父目录为根的子树导入**：

```text
example.com/app/
├── internal/
│   └── secret/        # 只有 example.com/app/... 下的包能导入
│       └── secret.go
├── api/
│   └── api.go         # 可以导入 example.com/app/internal/secret
└── main.go
```

模块外的代码尝试导入时会直接编译失败，实测（Go 1.27.1）：

```text
main.go:6:2: use of internal package intl/internal/secret not allowed
```

这是"公开 API"与"内部实现"之间最省事的边界：不用写文档声明"请勿使用"，编译器直接拦。

## 导出与可见性

Go 的可见性规则只有一条，但足够用：**标识符首字母大写 = 导出（别的包能访问），小写 = 未导出（只有本包能访问）**。

```go
package user

type User struct { // 导出
    Name  string // 导出
    email string // 未导出：只有 user 包内能用
}

func New(name string) *User { return &User{Name: name} } // 导出
func validate(u *User) bool  { return u.email != "" }    // 未导出
```

几点容易误会的：

- 规则看的是**标识符本身的首字母**，和它所在的类型是否导出无关。导出的结构体里可以有未导出字段。
- **未导出字段不会被子包或兄弟包访问到**，即使是同一个模块。跨包用不了就是跨包用不了，`friend` 之类的说法在 Go 里不存在。
- 未导出字段仍然参与 JSON 编解码的"忽略"规则（见 `26-JSON与序列化.md`），也仍然是 `reflect` 能看到的。
- 结构体字面量从别的包初始化时，**不能给未导出字段赋值**，所以导出的结构体要想让外部构造，通常配一个 `New` 函数。

这条规则也决定了你的 API 表面：**导出什么，就等于承诺什么**。多导出一个函数，就得为它的行为、命名、兼容性长期负责。

## 导入

### 分组与排序

```go
import (
    "fmt"
    "strings"

    "example.com/app/internal/store"
)
```

`gofmt` 会把同一组内的导入按字母序排列，但**不会帮你分组**。惯例是分成两组（标准库、第三方与本模块），中间空一行。少数项目把第三方和本模块再分成三组，也常见。

### 别名与两个特殊形式

```go
import (
    "fmt"
    f "fmt"                    // 别名：之后用 f.Println
    _ "net/http/pprof"         // 只执行 init，不使用包里的符号
    . "math"                   // 点导入：把符号直接引入本文件作用域（几乎不该用）
)
```

- **别名**最常见的用途是解决重名：`import jsonv2 "encoding/json/v2"`（见 `26-JSON与序列化.md`）。
- **空白导入 `_`** 用于"只要副作用"的包——典型是驱动注册（数据库驱动、`net/http/pprof` 的端点注册）。看到 `_` 导入就要意识到：这个包的价值在 `init` 里。
- **点导入 `.`** 会让代码里出现来源不明的符号，除了测试为了让语法贴近被导入包，实际项目基本不用。

**未使用的导入是编译错误**（不是警告）。这条规则看着烦，但它同时保证了导入列表就是你真实的依赖清单。

### 循环导入

`a` 导入 `b`、`b` 又导入 `a`，编译器会直接报 `import cycle not allowed`。这是 Go 里少数会被硬性拒绝的设计问题，遇到时**不要想着绕过，而要重新划分边界**。常见的解法：

- 把两边共用的类型抽到第三个包 `c`，让 `a` 和 `b` 都依赖 `c`。
- 把"接口"定义在**使用方**而不是实现方，让依赖方向单向化（这也是 Go 里"接受接口、返回具体类型"这条建议的由来，见 `12-接口.md`）。
- 把具体实现的注册改成在 `main` 包完成（依赖注入），让底层包只暴露接口。

## init 与初始化顺序

### 顺序是确定的

包级变量的初始化和 `init` 函数按固定顺序发生，实测（Go 1.27.1）：

```text
dep: 变量初始化     ← 1. 被导入的包先完成（变量 → init）
dep: init
main: 变量 a 初始化 ← 2. 本包的包级变量
main: 变量 b 初始化
main: init #1       ← 3. 本包的 init，按文件内出现顺序
main: init #2
main: main() 1 2    ← 4. 最后才是 main
```

两个细节值得记：

- **包级变量之间按"依赖关系"排序，而不是书写顺序**。写 `var c = b + 1` 在 `var b = f()` 之前，`b` 也会先算。
- 同一个文件里多个 `init` 按出现顺序执行；跨文件时按**文件名的字典序**（这依赖文件名，所以不要把有顺序要求的初始化拆到多个文件里）。

### init 函数

```go
func init() {
    // 每个包可以有任意多个 init
}
```

`init` 不能带参数、不能有返回值、不能被显式调用、也不能被引用为值。它唯一的作用就是在包加载时跑一次。

**什么时候该用**：注册（把实现注册进某个表）、修正无法用变量初始化表达式表达的默认值。

**什么时候不该用**，这才是更该记的部分：

- **不要用 `init` 做慢操作**：读文件、连数据库、发网络请求都会让"导入这个包"这个动作产生副作用和耗时，测试和构建都会变慢，而且失败时错误只能 panic 或静默吞掉。
- **不要用 `init` 传参**：它无法拿到任何调用方的输入，所以"可配置的初始化"只能靠显式函数调用。
- **能用显式函数就别用 `init`**：`MustLoadConfig(path)` 比 `init` 里偷偷读配置清楚得多——调用点看得见、错误能返回。

惰性初始化（真正的初始化推迟到第一次使用时）优先用 `sync.OnceFunc`/`sync.OnceValue`，见 `41-同步原语与内存模型.md`。

## 文档注释

`go doc` 和 pkg.go.dev 的文档**全部来自注释**，所以注释的写法有实际约束。

```go
// Package user 提供用户的创建与校验。
//
// 这个包不负责持久化，存储由调用方通过 Store 接口传入。
package user

// User 表示一个已注册用户。
type User struct {
    Name string
}

// New 用给定名字构造一个 User。
// 名字为空时返回错误。
func New(name string) (*User, error) { /* ... */ }
```

约定：

- **doc comment 紧贴在声明上方，中间不能空行**，紧跟的注释才是文档；空一行就变成普通注释了。
- **首句是摘要**，会被 `go doc` 单独取出来，所以首句要能独立成句，通常以被声明的名字开头（"New 用给定名字构造……"）。
- 包文档写在**任意一个**文件顶部的 `// Package xxx ...`，通常放在 `doc.go` 里。
- 标记已废弃用 `// Deprecated: 说明`，`go doc` 会单独渲染，IDE 会提示：

```go
// OldAPI 是旧接口。
//
// Deprecated: 用 NewAPI 代替。
func OldAPI() {}
```

想检查注释质量可以用 `golint` 系列的 linter（`staticcheck`、`revive` 都有对应规则，如"导出符号的注释应以符号名开头"）。`go vet` 本身**不做注释风格检查**，它关心的是可疑构造（见 `00-工具链.md`）。

## 构建约束

同一个包里，不同平台或架构需要不同实现时，用**构建约束**决定哪些文件参与编译。

```go
//go:build unix

package app

func platformName() string { return "unix" }
```

```go
//go:build windows

package app

func platformName() string { return "windows" }
```

规则：

- `//go:build` 必须出现在**文件最前面**，在它之前只能有空行和其他行注释。放到 `package` 下面会直接报错，实测（Go 1.27.1）：

  ```text
  ./plat.go:3:3: misplaced compiler directive
  ```

- 约束行和 `package` 之间按惯例空一行，`gofmt` 会自动补上（不空也能编译，但格式化后一定会变成空一行）。
- 条件支持 `&&`、`||`、`!` 和括号：`//go:build linux && amd64`、`//go:build !windows`。
- `unix` 是 Go 1.19 起支持的**通用约束**，覆盖所有类 Unix 系统，比逐个列 `linux || darwin || freebsd …` 清楚得多。
- 文件名后缀是更简单的写法：`foo_linux.go`、`foo_amd64.go`、`foo_linux_amd64.go` 会自动带上对应约束。**只有当条件表达不出来时（如 `!windows`）才需要用 `//go:build`。**
- 不要再用老的 `// +build` 形式，它从 Go 1.18 起就被 `//go:build` 取代，`go fix` 的 `plusbuild` 重写器可以自动迁移（见 `00-工具链.md`）。

常见用途：`os/signal` 里 `syscall.SIGTERM` 这类平台相关常量（见 `34-进程与信号.md`）、系统调用的不同实现、CGO 与非 CGO 两套实现。

## 交叉编译

只要不依赖 CGO，Go 的交叉编译就是两个环境变量的事：

```bash
GOOS=windows GOARCH=amd64 go build -o app.exe .
GOOS=darwin  GOARCH=arm64 go build -o app.mac .
GOOS=linux   GOARCH=arm64 go build -o app-arm64 .
```

不需要装目标平台的工具链——标准库会随目标平台一起重新编译。

两点注意：

- 用到的包如果依赖 CGO（例如 `net` 的某些解析器、`os/user`），交叉编译需要目标平台的 C 工具链。用 `CGO_ENABLED=0` 强制纯 Go 实现可以让大多数程序顺利交叉编译：

  ```bash
  CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o app .
  ```

- 想确认自己到底在什么平台上跑，用 `runtime.GOOS` / `runtime.GOARCH`；构建期的判断（决定编哪个文件）用构建约束，运行期的判断用这两个常量，两者不要混。

## go generate

`go generate` 用来跑**代码生成**：它扫描源码里的 `//go:generate` 指令并逐条执行。

```go
//go:generate stringer -type=Level
type Level int

const (
    LevelDebug Level = iota
    LevelInfo
)
```

```bash
go generate ./...
```

要点：

- **`go generate` 不参与构建**，也不做依赖管理。它只是"帮你把写在注释里的命令跑一遍"，所以要在生成新代码后手动（或在 CI / `make` 里）执行。
- 生成的文件在头部加上 `// Code generated by ... DO NOT EDIT.`，这条标记有实际作用：`gofmt`、`go vet` 和多数 linter 会据此调整检查策略，人也一眼能看出不要手改。
- 生成工具本身要是可复现的依赖，通常用 `tools.go` 的方式把它记进 `go.mod`（见下节）。
- 生成代码的最大价值是**消除手写的重复**：枚举的字符串方法、序列化代码、mock、协议绑定。判断标准很简单——如果一处改动需要同步修改好几处机械重复的代码，就该生成。

## 模块与依赖

### go.mod 与 go.sum

模块由 `go.mod` 定义，它声明模块路径、语言版本和依赖：

```text
module example.com/app

go 1.27.1

require (
    example.com/lib v1.2.3
)

replace example.com/lib => ../lib
```

- **`module`** 那一行是**导入路径前缀**，别人的 `import` 要用它。
- **`go`** 指令既是语言版本门槛（见 `00-工具链.md` 的"语言版本门槛"），也决定默认的 GODEBUG 行为。
- **`toolchain`**（Go 1.21 起）声明"构建这个模块至少用哪个工具链"。它和 `go` 指令是两件事：`go` 说的是**语言特性门槛**，`toolchain` 说的是**用哪个 go 命令**。本地工具链版本不够时，`GOTOOLCHAIN=auto`（默认）会去下载指定的工具链——离线环境会直接报错：

  ```text
  go: downloading go1.28.0 (linux/amd64)
  go: download go1.28.0 for linux/amd64: toolchain not available
  ```

  平时更常见的是**让工具顺手写下的一行**：`go mod tidy`、`go mod edit -toolchain=...` 都可能加它。实测一条容易困惑的规则——**当 `toolchain` 与 `go` 指令本身要求的版本完全相同时，`go mod tidy` 会把它删掉**（例如 `go 1.27.1` + `toolchain go1.27.1`），写成别的版本（更高、或只是补丁号不同，如 `go1.27.0`）则会保留。所以"tidy 之后我那行没了"通常不是出问题，只是它本来就没提供额外信息。要固定工具链版本就用 `go mod edit -toolchain=go1.28.0` 显式写，并把它提交进版本库。
- `go.sum` 记录依赖内容的校验和，**要提交进版本库**；它保证你拿到的依赖和上次构建时逐字节一致。

### 增删依赖

```bash
go get example.com/lib@v1.2.3   # 添加/升级到指定版本
go get example.com/lib@latest   # 升到最新
go get -u ./...                 # 升级所有依赖（慎用，要跑测试）
go mod tidy                     # 补齐缺失的、删掉没用的依赖
```

`go mod tidy` 是最常用的一个：它按源码里真实的 `import` 重新计算依赖集合。**改完代码、尤其是删掉某些功能之后，跑一下 `go mod tidy` 是好习惯。**

### replace、vendor 与工作区

三者的分工一句话说清：**`replace` 改单个模块的依赖指向（临时调试、本地联调），`go.work` 管一组本地模块（多仓库同时开发），`vendor` 把依赖固化进仓库（构建不依赖网络）**；它们不是替代关系，可以只用一个，也可以在不同阶段切换。

- **`replace`** 把某个依赖指向本地路径或另一个版本，常见于"同时改主项目和依赖库"的时候。注意 `replace` **只影响当前模块**，不会传递给使用者，所以不要用它来表达"我们依赖某个 fork"这类团队约定。
- **`go mod vendor`** 把依赖复制进 `vendor/` 目录，之后构建默认只用这份副本。作用是构建不依赖网络、代码可审计；代价是仓库体积和升级时的一次性同步。用了 vendor 之后所有 `go` 命令都要记得 `-mod=vendor`（Go 1.14 起有 `vendor/modules.txt` 时会自动启用）。
- **`go.work`**（Go 1.18 起）用于**多模块工作区**：让几个本地模块互相引用时不用逐个 `replace`。实测效果：

  ```bash
  # 没有 go.work 时，app 引用未发布到远端的 lib 会失败：
  #   main.go:3:8: no required module provides package example.com/lib; to add it:
  #       go get example.com/lib

  go work init ./app ./lib   # 生成 go.work
  cd app && go build .       # 成功
  ```

  `go.work` 是**开发期的本地设施，不要提交进仓库**（通常加进 `.gitignore`），否则会覆盖别人的依赖解析。事后加模块用 `go work use ./pkg`（也可以用 `-r` 递归加一个目录下的所有模块），`go work edit` 能读写 `go.work` 里的 `use`/`replace`——`replace` 写在 `go.work` 里只对工作区生效，比写在 `go.mod` 里更适合"本地临时替换"。

### 把工具也记进依赖

代码生成器、linter 这类"只在开发时用"的命令行工具，也应该有版本记录。标准做法是建一个 `tools.go`：

```go
//go:build tools

package tools

import (
    _ "golang.org/x/tools/cmd/stringer"
)
```

它的作用是让 `go mod tidy` **认为这些工具是项目依赖**，从而把版本固定进 `go.mod`，同时又不会被编进你的程序（构建约束 `tools` 平时不满足）。

## 常见错误与建议

- **未使用的导入/变量是编译错误**。这不是啰嗦，而是强制你保持依赖清单干净；用 `_ = x` 或 `_` 导入来"消掉"之前先想一下是不是真的没用。
- **包名重复导入冲突**：两个包同名时用别名，别用点导入。
- **把 `init` 当构造函数用**：需要参数、需要返回错误、需要被测试替换的初始化，都不该放进 `init`。
- **在包里放太多东西**：一个包应该围绕**一个概念**。`util`、`common`、`helper` 这类包名是设计信号——它说明这里没想清楚职责。
- **过早拆包**：包边界是有成本的（循环导入、导出规则的额外一层）。先在一个包里写清楚，等它确实变大、或者确实需要隔离可见性时再拆。
- **导出得太多**：导出即承诺。不确定要不要导出的，先不导出——加一个导出符号是兼容性变更，去掉一个则是破坏性变更。
- **循环导入**：几乎总是"职责划分错了"的信号，解法见上文。
- **`go mod tidy` 之后要提交 `go.mod` 和 `go.sum`**：只提交其中一个会让别人构建出不同的依赖。
