# 39 38 并发基础

> Go 版本：>= 1.27.1  
> 相关标准库：sync、time

并发是 Go 的语言级特性：`go` 和 `chan` 都是关键字。这一篇用三个互不相干的活做例子：煮水（100ms）、烤面包（80ms）、煎蛋（30ms）——**顺序做要 210ms，同时做只要 100ms**。

示例里会用到 `time.Sleep`、`time.After`、`time.Second`（见 `24-时间.md`）：这里的 `time.Sleep` 只用来**模拟慢操作**，不是协调并发的手段。耗时本身随机器变化，所以只断言"关系"（比如"总耗时大于 200ms"），不写死数字。

`go` 后面跟的是函数调用，所以读这一篇要先熟悉函数值与闭包（`04-函数.md`）。

并发这一组共四篇，建议按顺序读：本篇是基础工具（goroutine、channel、`select`），`40-context.md` 讲取消与超时，`41-同步原语与内存模型.md` 讲共享状态怎么同步（末尾的内存模型偏理论，觉得抽象可以先跳），`42-并发模式与运行时行为.md` 讲怎么组织并发、以及出事时怎么排查。只想快点上手的话，读完本篇的 channel 与 `select` 就能写不少代码了。

## 串行做：总耗时是三段之和

三个活各自返回自己花掉的毫秒数。为什么要返回？因为这样我们才能确认"每个活都回来了"，而不是只知道"都做完了"。

```go
// boilWater 煮水（100ms）、toast 烤面包（80ms）、fryEgg 煎蛋（30ms）
func boilWater() int { time.Sleep(100 * time.Millisecond); return 100 }
func toast() int { time.Sleep(80 * time.Millisecond); return 80 }
func fryEgg() int { time.Sleep(30 * time.Millisecond); return 30 }

start := time.Now()

total := boilWater() + toast() + fryEgg()

fmt.Println(total) // 210 —— 三个耗时相加
fmt.Println(time.Since(start) > 200*time.Millisecond) // true —— 总耗时就是它们之和
```

一件事做完才做下一件，总耗时是三者相加，这是后面所有对比的标尺。

## goroutine：启动之后没人管

`go` 把函数丢到新的 goroutine 里执行，然后立刻返回：

```go
// boilWater 煮水（100ms）、toast 烤面包（80ms）、fryEgg 煎蛋（30ms）
func boilWater() int { time.Sleep(100 * time.Millisecond); return 100 }
func toast() int { time.Sleep(80 * time.Millisecond); return 80 }
func fryEgg() int { time.Sleep(30 * time.Millisecond); return 30 }

start := time.Now()

go boilWater() // go 语句里返回值会被丢掉，先不管
go toast()
go fryEgg()

fmt.Println(time.Since(start) < 100*time.Millisecond) // true —— 主 goroutine 没等它们就往下走了
```

程序到这里就结束了：主 goroutine 一退出，程序结束，其他 goroutine 不会继续运行，所以三个活多半还没做完，结果也没人接。

`go` 只负责"启动"，不负责"做完了没有"，也不负责把结果交回来。

goroutine 之所以能这么随便开，是因为它比操作系统线程便宜得多：**栈很小且按需增长**，而且由运行时在用户态调度，不需要为每个 goroutine 准备一份 MB 级的线程栈。实测一下就知道量级：

```go
const n = 100_000

block := make(chan struct{})
for range n {
    go func() { <-block }() // 都停在这里，保持存活
}

for runtime.NumGoroutine() < n {
    time.Sleep(10 * time.Millisecond) // 等它们都起来
}

var m runtime.MemStats
runtime.ReadMemStats(&m)

fmt.Println(runtime.NumGoroutine() >= n)                     // true —— 十万个同时存活
fmt.Println(m.StackInuse/uint64(n) < 64*1024)                // true —— 平均每个 goroutine 的栈是 KiB 量级

close(block)
```

本机实测这十万个 goroutine 合计约 196 MiB，平均每个约 2 KiB。起始栈大小**不是固定值**：运行时会根据 GC 扫描到的平均栈大小动态调整新 goroutine 的起始栈（`runtime` 里的 `startingStackSize`），栈不够用时会自动增长、空闲时也会收缩。

所以真正要限制的是**文件描述符、连接、内存这类外部资源**，而不是 goroutine 的个数——并发度该限多少，取决于下游能承受多少，而不是"goroutine 很贵"（限流手段见 `42-并发模式与运行时行为.md`）。

## sync.WaitGroup：等它们都做完

```go
// boilWater 煮水（100ms）、toast 烤面包（80ms）、fryEgg 煎蛋（30ms）
func boilWater() int { time.Sleep(100 * time.Millisecond); return 100 }
func toast() int { time.Sleep(80 * time.Millisecond); return 80 }
func fryEgg() int { time.Sleep(30 * time.Millisecond); return 30 }

start := time.Now()

var wg sync.WaitGroup

wg.Go(func() { boilWater() }) // 结果先丢掉：这里只解决“做完了没有”
wg.Go(func() { toast() })
wg.Go(func() { fryEgg() })

wg.Wait()

fmt.Println(time.Since(start) >= 100*time.Millisecond) // true —— 等到最慢的那个也结束才往下走
```

`sync.WaitGroup` 只回答一个问题：**它们都干完了吗**。它不知道结果，所以上面只能把返回值丢掉——"结果怎么拿回来"是下一节。`wg.Go`（Go 1.25 起）等价于 `wg.Add(1)` 加一个 `go`，传进去的函数不能 panic；传统写法见后文，`Add` 必须在 `Wait` 之前调用。

## channel：把结果收回来

`channel` 用来在 goroutine 之间传数据：

```go
// boilWater 煮水（100ms）、toast 烤面包（80ms）、fryEgg 煎蛋（30ms）
func boilWater() int { time.Sleep(100 * time.Millisecond); return 100 }
func toast() int { time.Sleep(80 * time.Millisecond); return 80 }
func fryEgg() int { time.Sleep(30 * time.Millisecond); return 30 }

results := make(chan int, 3) // 缓冲 3：三个活各交一个结果，谁也不挡谁
var wg sync.WaitGroup

wg.Go(func() { results <- boilWater() })
wg.Go(func() { results <- toast() })
wg.Go(func() { results <- fryEgg() })

wg.Wait()

got := []int{<-results, <-results, <-results} // 结果有几个是已知的，收三次就够
slices.Sort(got)

fmt.Println(got) // [30 80 100] —— 到达顺序不确定，排序之后才是确定的
```

`WaitGroup` 管"结束"，`channel` 管"数据"，两者配合是并发里最常用的组合。注意收上来的顺序不固定（谁先做完谁先交）：**并发程序里"结果确定、顺序不确定"是常态**，所以断言之前先排序，或者按任务编号归位。

## close 与 range：什么时候算结束

上一节靠"我知道只有三个结果"来收尾。真实代码里这个数量常常是算出来的、甚至中途会变，于是需要一种方式表达"**不会再有值了**"：

```go
// boilWater 煮水（100ms）、toast 烤面包（80ms）、fryEgg 煎蛋（30ms）
func boilWater() int { time.Sleep(100 * time.Millisecond); return 100 }
func toast() int { time.Sleep(80 * time.Millisecond); return 80 }
func fryEgg() int { time.Sleep(30 * time.Millisecond); return 30 }

results := make(chan int, 3)
var wg sync.WaitGroup

wg.Go(func() { results <- boilWater() })
wg.Go(func() { results <- toast() })
wg.Go(func() { results <- fryEgg() })

go func() {
    wg.Wait()
    close(results) // 发送方关闭：告诉接收方"不会再有值了"
}()

var got []int
for v := range results { // 关闭之后 range 自然结束
    got = append(got, v)
}

slices.Sort(got)

fmt.Println(got) // [30 80 100]
```

关闭是**发送方的动作**，而且要在"确实不会再发"之后才做，所以这里是先 `wg.Wait()` 再 `close`。两条规矩：不要从接收方关闭 channel；向已关闭的 channel 发送会 panic。更多细节见后面"关闭 channel 之后"。

## 数据竞争：共享变量会丢更新

前面每个 goroutine 都只算自己的活，结果走 channel 回来。一旦两个 goroutine 要改**同一个变量**，就没这么太平了：

```go
total := 0
var wg sync.WaitGroup

for range 100 {
    wg.Go(func() {
        total++ // 不是原子操作：读出来、加一、写回，中间可能被打断
    })
}

wg.Wait()

fmt.Println(total) // 结果不确定：可能是 100，也可能更小，不要依赖任何具体值
```

**不要指望它是 100，也不要依赖任何具体值**。`total++` 是三步：读出旧值、加一、写回；两个 goroutine 同时读到同一个旧值，就会丢掉一次自增，这就是**数据竞争**。"100 或更小"是当前实现在 64 位平台上跑出来的常见结果，不是语言给的保证——规范只说这类读不能凭空捏造值（见 `41-同步原语与内存模型.md` 的"内存模型"一节），任何具体数值都不该写进断言。这段代码唯一能断言的是"它需要同步"。

把上面这段存成文件后跑 `go run -race .`，会看到 `WARNING: DATA RACE` 加两条相反的调用栈（命令见 `00-工具链.md` 的"go test -race 与 go run -race"一节）。`wg.Wait()` 是必须的：主 goroutine 先退出的话，竞争根本来不及发生。还要记住**竞争不一定每次都出错**，它常在压力大、调度恰好错开时才暴露，所以要用 `-race` 验证，不能"跑一次没出错就算了"。

## sync.Mutex：把竞争修好

```go
var mu sync.Mutex
total := 0
var wg sync.WaitGroup

for range 100 {
    wg.Go(func() {
        mu.Lock() // 临界区：同一时刻只允许一个 goroutine 进入
        total++
        mu.Unlock()
    })
}

wg.Wait()

fmt.Println(total) // 100 —— 加锁之后不再丢更新
```

函数里用 `defer mu.Unlock()` 更稳妥（有多个 `return` 分支也不会漏解锁）。**锁为什么能让上面那些改写变得安全**——"一个 goroutine 写的值，另一个什么时候一定看得到"——属于内存模型的范畴，见 `41-同步原语与内存模型.md`。

## 无缓冲与有缓冲

无缓冲 channel 的发送和接收必须同时准备好，否则会阻塞——**收到值的那一刻，发送方一定已经把值交出来了，所以交接点同时是一次同步点**：

```go
ch := make(chan int)

go func() { ch <- 10 }()

fmt.Println(<-ch) // 10
```

有缓冲 channel 则允许发送方先跑一段：

```go
ch := make(chan int, 2)

ch <- 1 // 缓冲区没满，不阻塞
ch <- 2

fmt.Println(<-ch, <-ch) // 1 2
```

缓冲区满时继续发送会阻塞，空时继续接收会阻塞。缓冲不改变语义（仍然先进先出），改变的是"发送方能不能先走一段"。

## channel 方向

函数参数可以限制 channel 方向：

```go
func send(ch chan<- int) {
    ch <- 1
}

func receive(ch <-chan int) {
    fmt.Println(<-ch)
}
```

这样可以明确谁负责发送、谁负责接收：方向写进签名之后，"谁会 close"这个问题就只剩一个答案了。

## 关闭 channel 之后

关闭是发送方的动作。**向已关闭的 channel 发送会 panic**；但**读**没问题——缓冲里的剩余数据照旧能取完（`range` 就是干这个的，见前面"close 与 range"）。

另一个容易踩的点：**已关闭的 channel 永远"就绪"**。缓冲取空之后，接收会立刻返回零值且 `ok == false`，所以下面的循环一旦 `chA` 关闭就会开始空转：

```go
// 反例：chA 关闭后这个 case 仍然每轮“就绪”
for {
    select {
    case v, ok := <-chA:
        if !ok {
            continue // 无限空转：chA 已经是关闭状态，下一轮立刻又能选中
        }
        handle(v)
    case v := <-chB:
        handle(v)
    }
}
```

正确做法是读到关闭就把这个变量置 `nil`，让 `select` 不再考虑它（见下一节）。

## select

`select` 同时等待多个 channel：

```go
select {
case v := <-ch1:
    fmt.Println("ch1:", v) // 走哪个 case 取决于谁先就绪；同时就绪时随机，不能依赖书写顺序
case v := <-ch2:
    fmt.Println("ch2:", v)
}
```

没有 case 准备好时，`select` 会阻塞。

### 公平性

多个 case **同时**就绪时，`select` **均匀随机**地选一个，所以**任何处理顺序都不能被依赖**：不能假设“按 case 书写的顺序优先”，也不能用 `select` 表达优先级。

下面这段可以自己跑，验证它确实是随机的：

```go
a := make(chan int, 1)
b := make(chan int, 1)
ca, cb := 0, 0

for range 200 {
    a <- 1
    b <- 1

    select {
    case <-a:
        ca++
    case <-b:
        cb++
    }

    // 排空没被选中的那个，下一轮才能重新同时就绪
    select { case <-a: default: }
    select { case <-b: default: }
}

fmt.Println(ca, cb) // 连续几次运行：101 99、88 112、97 103——都在 100 上下浮动
```

`ca` 和 `cb` 谁多谁少每次运行都不同，但 200 轮一定消费掉 200 个值：想写断言就断言这个守恒量。

### default

```go
select {
case v := <-ch:
    fmt.Println(v)
default:
    fmt.Println("no data") // ch 里没有数据时立刻走这里，不会阻塞
}
```

`default` 让 `select` 不阻塞：轮询式收结果、给上报做一条"攒够就发、否则先干别的"的快速路径，都靠它。

### 超时

```go
select {
case v := <-ch:
    fmt.Println("received:", v)
case <-time.After(time.Second):
    fmt.Println("timeout") // ch 在一秒内没有数据就走这里，取决于 ch 的时序
}
```

（`time.After` 在循环里每次都会新建一个 timer，开销和分配都在；但**不再需要**为回收问题改用 `time.NewTimer`——Go 1.23 起 GC 能回收未 `Stop` 的 timer，`select` 里直接用 `time.After` 是可以接受的。见 `24-时间.md`。）

### nil channel：禁用一个 case

**nil channel 上的发送和接收会永远阻塞。** 这一点配合 `select` 就变成了一个非常实用的技巧：把某个 case 引用的 channel 变量设为 `nil`，就等于**关掉这个分支**，而不是让它每轮都白白参与一次随机选择。

```go
chA := make(chan int)
chB := make(chan int)

go func() { chA <- 1; close(chA) }()
go func() { chB <- 2; close(chB) }()

var gotA, gotB []int

for chA != nil || chB != nil {
    select {
    case v, ok := <-chA:
        if !ok {
            chA = nil // 之后 select 不再考虑这个 case
            continue
        }
        gotA = append(gotA, v)
    case v, ok := <-chB:
        if !ok {
            chB = nil
            continue
        }
        gotB = append(gotB, v)
    }
}

fmt.Println(gotA, gotB) // [1] [2]
```

循环条件写成 `chA != nil || chB != nil`，两个都置 nil 后循环自然结束。这个模式就是“**读完就禁用**”，处理多个来源、每个来源只关心它自己的结束时机时非常常用。

同一招也可以用来做“等待多个信号都到达”：

```go
sigA := make(chan struct{}, 1)
sigB := make(chan struct{}, 1)

remaining := 2

for remaining > 0 {
    select {
    case <-sigA:
        sigA = nil // 置 nil 保证同一路信号不会被消费两次
        remaining--
    case <-sigB:
        sigB = nil
        remaining--
    }
}
```

以及显式声明一个 nil channel 来“占位”，让某个分支在特定状态下永不参与随机：

```go
var never <-chan struct{} // nil channel

select {
case <-ch:
    // 正常路径
case <-never: // 永远不会被选中
case <-time.After(time.Second):
    // 超时路径
}
```

两点注意：

- 置 `nil` 改的是 `select` 语句里**引用的那个变量**，所以它必须是可赋值的（局部变量或函数参数都可以；如果是结构体字段或从 slice/map 里取的值，先拷到局部变量再置 nil）。
- “所有 case 的 channel 都是 nil 且没有 `default`”会让 `select` **永久阻塞**，这在某些场景下是有意为之（就是“此 goroutine 睡死”），但更多时候是 bug：检查一下是不是忘了给某个变量赋值就置了 nil。

## WaitGroup 的传统写法

`wg.Go` 之外，也可以自己 `Add` / `Done`：

```go
var wg sync.WaitGroup

wg.Add(1)

go func() {
    defer wg.Done()
    fmt.Println("done")
}()

wg.Wait()
```

`Add` 必须在 `Wait` 之前调用。

`wg.Go` 只覆盖"起一个 goroutine 就记一笔"这一种形状；**计数与起 goroutine 分开**时仍然要用 `Add`/`Done`，例如 4 个 worker 领 N 个活，计数按"活"的数量一次记上（`wg.Add(len(jobs))`），每个活处理完各自 `Done`。反过来，`Add(1)` + `go` + `Done` 这种一对一的旧写法，官方已经在用 `go fix` 的 `waitgroupgo` 重写器自动改写成 `wg.Go`（见 `00-工具链.md` 的“go fix：现代化重写器”一节）。

## RWMutex

读多写少时可以用 `sync.RWMutex`：`RLock` / `RUnlock` 是读锁，多个读可以并发、与写锁互斥；`Lock` / `Unlock` 是写锁，同一时刻只允许一个持有者。

```go
var mu sync.RWMutex
m := map[string]int{}

mu.RLock()
v := m["a"]
mu.RUnlock()

mu.Lock()
m["a"] = 1
mu.Unlock()
```

多个 goroutine 同时读写同一个 map 会触发**致命错误**（不是普通 panic，`defer` 和 `recover` 都拦不住），所以要在编码阶段就设计好保护，见 `08-map.md`。

## 数据竞争与死锁

用 `go test -race` / `go run -race` 可以发现数据竞争，命令用法见 `00-工具链.md`。

死锁常见原因：

- 无缓冲 channel 同时等待对方
- 加锁顺序不一致
- WaitGroup 计数不匹配
- goroutine 永久阻塞
