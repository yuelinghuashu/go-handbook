## sync 的常用类型：Map、Once 与 Cond

### sync.Map

`sync.Map` 是一个并发安全的 map，用它可以省掉自己加锁。但**它不是普通 map 的替代品**——标准库文档写得很直白：*“Most code should use a plain Go map instead, with separate locking”*。原因是 `sync.Map` 的键值类型是 `any`（丢掉类型安全），而且没有 `len`、不能和其他不变量一起维护。

它只对两种访问模式有优势：

1. **键只写一次、之后反复读**，例如只增不减的缓存。这种场景用 `LoadOrStore` 天然去重。
2. **多个 goroutine 读写互不相交的键集合**。

这两种情况下它的锁竞争显著低于 `map` 配 `RWMutex`；其他情况用它往往更慢也更难维护。

```go
var m sync.Map

// 1. 只写一次的缓存：LoadOrStore 不会覆盖已有值
actual, loaded := m.LoadOrStore("k1", "first")
fmt.Println(actual, loaded) // first false

actual, loaded = m.LoadOrStore("k1", "second")
fmt.Println(actual, loaded) // first true——第二次没有覆盖

// 读取、写入、删除
v, ok := m.Load("k1")
m.Store("k2", "v2")
m.Delete("k2")
fmt.Println(v, ok) // first true

// 遍历用 Range，回调返回 false 可提前结束
m.Range(func(k, v any) bool {
    fmt.Println(k, v)
    return true
})
```

三个使用上的注意点：

- 没有 `len`，要计数只能用 `Range` 累加，这也是它不适合当“带长度语义的集合”的原因。
- `Range` 不保证一致性快照：遍历期间其他 goroutine 的读写可能可见也可能不可见。
- 它**零值可用**，不需要 `make`，也不能拷贝（和所有 `sync` 类型一样）。

绝大多数场景直接用 `map` 加 `sync.RWMutex` 即可，写法见 `38-并发基础.md`。

### Once

```go
var once sync.Once

once.Do(func() {
    fmt.Println("only once")
})
```

`sync.Once` 适合初始化配置、连接池和全局资源。

### OnceFunc、OnceValue 与 OnceValues

Go 1.21 起 `sync` 提供了三个包装函数，把“`sync.Once` + 一个包级变量”的两段式写法压缩成一行。它们直接替代上面那种需要自己声明 `var once sync.Once`、再把结果存到别处的模式：

```go
// 只执行一次，无返回值
cleanup := sync.OnceFunc(func() {
    fmt.Println("cleanup")
})

cleanup()
cleanup() // 不再执行

// 只执行一次并返回一个值
type Config struct{ Addr string }

loadConfig := sync.OnceValue(func() *Config {
    fmt.Println("load config")
    return &Config{Addr: ":8080"}
})

c1 := loadConfig()
c2 := loadConfig() // 复用第一次的结果

fmt.Println(c1 == c2) // true
```

```go
// 返回两个值：最典型的是 值 + error
connect := sync.OnceValues(func() (string, error) {
    return "dsn", nil
})

dsn, err := connect()
fmt.Println(dsn, err) // dsn <nil>
```

关键语义：

- 返回的函数**可以并发调用**，只有第一次会真正执行 `f`，其余调用会等待它返回（和 `sync.Once.Do` 一致）。
- 如果 `f` **panic**，返回的函数在之后**每次**调用都会用**同样的值**再次 panic。不会出现“标记为已执行，但其实没拿到结果”的半成品状态。
- `OnceValues` 的两个类型参数是自由的，`func() (T, error)`、`func() (T, bool)`、`func() (*Conn, error)` 都可以；**它最多只支持两个返回值**，需要三个（例如 `func() (*Conn, func(), error)`）就得自己用 `sync.Once` 包一层。
- 惰性初始化全局资源时优先用它们，比“包级变量 + `init()` + `sync.Once`”更清晰：没有全局可变状态，返回值类型自动推断，也不用担心别人绕过初始化逻辑直接用变量。

`sync.Once` 本身仍然有用：需要在初始化过程中做更细的控制（例如自己决定何时进入等待、或者需要在 `Do` 之外持有同一把锁）时才需要它。普通场景优先用这三个函数。

### Cond

`sync.Cond` 适合等待某个条件成立：

```go
var mu sync.Mutex
cond := sync.NewCond(&mu)
ready := false

go func() {
    mu.Lock()
    ready = true
    cond.Broadcast()
    mu.Unlock()
}()

mu.Lock()
for !ready {
    cond.Wait()
}
mu.Unlock()
```

大多数场景优先使用 channel，只有确实需要广播条件变量时再使用 `sync.Cond`。

## atomic

`sync/atomic` 提供原子操作，适合简单计数器：

```go
var count atomic.Int64

count.Add(1)
count.Add(2)

fmt.Println(count.Load()) // 3
```

原子操作只保护单个值。复杂共享状态仍然需要使用 mutex 或 channel。

### Bool 与 Pointer[T]

`atomic.Int64` 之外，日常最常用的就是 `atomic.Bool` 和 `atomic.Pointer[T]`。这一组带类型的原子类型（`Int32` / `Int64` / `Uint32` / `Uint64` / `Bool` / `Pointer[T]` 等）都是 Go 1.19 引入的，方法集完全一致：`Load` / `Store` / `Swap` / `CompareAndSwap`。（更早的 `atomic.Value` 自 Go 1.4 起就有，能存任意类型，但会丢掉类型安全。）

```go
var ready atomic.Bool

// Load：原子读；零值就是 false，不需要显式初始化
fmt.Println(ready.Load())                        // false —— 零值就是 false

// Store：原子写
ready.Store(true)

fmt.Println(ready.Load())                        // true
// CompareAndSwap：当前值等于第一个参数时才写入第二个参数，返回是否交换成功
fmt.Println(ready.CompareAndSwap(true, false))   // true
// Swap：写入新值并返回旧值
fmt.Println(ready.Swap(true))                    // false —— 返回旧值
```

用 `atomic.Bool` 而不是 `int32` 加 `atomic.LoadInt32`，好处是可读性：`ready.Load()` 一眼就懂，不用在脑子里维护“0 是 false、1 是 true”的约定。

`atomic.Pointer[T]` 是**泛型**原子指针，`Load` 直接返回 `*T`，不需要任何类型断言：

```go
type Config struct{ Addr string }

var cfg atomic.Pointer[Config]

// Store：原子地发布一个新指针
cfg.Store(&Config{Addr: ":8080"})

// Load：原子读取，返回类型就是 *Config（不需要类型断言）
c := cfg.Load()          // 类型就是 *Config
fmt.Println(c.Addr)      // :8080

// Swap：写入新指针并返回旧指针
old := cfg.Swap(&Config{Addr: ":9090"})
fmt.Println(old.Addr)    // :8080
fmt.Println(cfg.Load().Addr) // :9090

// 零值是 nil *T，没 Store 过也能安全 Load
var empty atomic.Pointer[Config]
fmt.Println(empty.Load() == nil) // true —— 零值是 nil *T
```

**为什么它比 `unsafe.Pointer` + `atomic.LoadPointer` 好**：

- `atomic.LoadPointer` 返回 `unsafe.Pointer`，必须手工写成 `(*Config)(p)` 才能用。这个转换写错了、或者转成了错误的类型，**编译器一点都不会拦**，要等运行时才以难以复现的内存错误暴露出来。`atomic.Pointer[T]` 把类型检查交给编译器。
- `sync/atomic` 文档在四个旧函数上都写了推荐语：`LoadPointer` → “Consider using the more ergonomic and less error-prone `Pointer.Load` instead”，`StorePointer` / `SwapPointer` / `CompareAndSwapPointer` 各自指向对应的方法。也就是说标准库自己就把这套泛型类型定位成替代品。
- 旧 API 还需要你自己保证 `unsafe.Pointer` 的对齐和生命周期规则（例如不能指向已被回收的对象），这些都是 `atomic.Pointer[T]` 由编译器代劳的。

补充两个所有 `atomic` 类型都适用的约束（文档明确写了）：

- **首次使用后不可复制。** 类型里带 `noCopy` 字段，`atomic.Bool`、`atomic.Int64`、`atomic.Pointer[T]`、`atomic.Value` 都是如此。所以不要把它们按值嵌进会被复制的结构体，也不要用 `append` 把它们放进切片——需要共享就传指针（`*atomic.Int64`），或者在结构体里以指针字段持有。
- 零值可用：`atomic.Bool` 零值是 `false`，`atomic.Pointer[T]` 零值是 `nil *T`，`atomic.Int64` 零值是 0。不需要显式初始化。

需要存**任意类型**、又不想引入泛型时用 `atomic.Value`，代价是取出来要做类型断言，而且同一个 `Value` 存过的类型**必须始终一致**：

```go
var snapshot atomic.Value

// Store：存一个值（类型由第一次 Store 固定下来）
snapshot.Store([]int{1, 2, 3})
// Load：取回值，拿到的是 any，要自己断言回原类型
fmt.Println(snapshot.Load().([]int)) // [1 2 3]

snapshot.Store([]int{4}) // 类型相同，允许
// snapshot.Store("s")
// panic: sync/atomic: store of inconsistently typed value into Value
```

这个 panic 是运行时的，编译期看不出来——把 `atomic.Value` 用在“有时存 A 有时存 B”的场景会直接炸（`Store(nil)` 同样 panic）。类型固定时用 `atomic.Pointer[T]` 更好：类型安全、存取不用接口装箱和类型断言，`Load` 也不用处理“第一次 Store 还没完成”的中间状态。

### CompareAndSwap 循环

`CompareAndSwap`（CAS）的语义是“如果当前值等于 old，就换成 new 并返回 true；否则什么都不做并返回 false”。

```go
if counter.CompareAndSwap(3, 4) {
    // 当时确实是 3，已经改成 4
}
```

它最典型的用法是**读-改-写循环**：CAS 失败说明有人抢先改了，重新读一次再试。

```go
var counter atomic.Int64

func increment() {
    for {
        old := counter.Load()
        if counter.CompareAndSwap(old, old+1) {
            return
        }
    }
}
```

不过这个例子只是演示：计数器本身就应该是简单的 `counter.Add(1)`（`Add` 已经是原子的，不需要重试）。真正需要 CAS 循环的是**“基于当前值算出新值”的复合更新**：

```go
type Config struct{ Addr string }

var cfg atomic.Pointer[Config]

func setAddr(addr string) {
    for {
        old := cfg.Load()
        next := &Config{Addr: addr}

        if cfg.CompareAndSwap(old, next) {
            return
        }
        // 失败：期间有别的 goroutine 改过 cfg，重新读再算一次
    }
}
```

注意两点：

- CAS 比较的是**指针本身**（地址是否相等），不是指向的内容是否相等。所以上例里每次都新建 `next` 也没问题——只要 `cfg` 里存的还是同一个 `old` 指针，就交换成功。
- CAS 循环适合**低竞争**场景。竞争激烈时大量 goroutine 反复失败空转，CPU 白烧，这时候改用 `sync.Mutex` 反而更简单也更快。“CAS 一定比锁快”是错的，要看冲突率。

## 内存模型

**这一节是理论收尾，初读可以跳过**——如果你只用 channel、`WaitGroup` 和 `Mutex`，前面几节的用法已经够用；但如果你用了 `sync/atomic`、或者想知道"加锁到底保证了什么"，下面这些规则就是必须的。

Go 的内存模型定义的是 **happens-before（先行发生）** 关系：它规定了在什么条件下，一个 goroutine 里的读**保证**能看到另一个 goroutine 里的写。没有同步，就没有任何保证——不是“可能会看到旧值”，而是“没有任何承诺”。

建立 happens-before 的常见操作（完整定义见 `go doc` 里的 *The Go Memory Model*，即 GOROOT 下的 `doc/go_mem.html`）：

- **goroutine 创建**：启动它的 `go` 语句先行发生于新 goroutine 的执行开始。
- **channel**：发送先行发生于对应的接收完成；channel 的关闭先行发生于“因关闭而返回零值”的接收；无缓冲 channel 的接收先行发生于对应发送的完成；容量为 C 的 channel 的第 k 次接收先行发生于第 k+C 次发送的完成（这条把缓冲 channel 变成了计数信号量）。
- **Mutex / RWMutex**：第 n 次 `Unlock` 先行发生于第 m（m > n）次 `Lock` 返回。
- **sync.Once**：`once.Do(f)` 中 `f` 的完成先行发生于**任何一次** `once.Do(f)` 的返回。
- **sync/atomic**：原子操作之间是顺序一致（sequentially consistent）的，等价于 C++ 的 sequentially consistent atomics、Java 的 volatile。

反过来，**goroutine 的退出不保证先行发生于程序中的任何事件**。所以下面这种写法不保证打印出新值：

```go
var a string

func hello() {
    go func() { a = "hello" }()
    print(a) // 不保证打印出 hello，也可能是空串
}
```

必须用 channel、`WaitGroup` 或锁显式建立同步。`38-并发基础.md` 的 `## sync.WaitGroup` 强调的“`Add` 必须在 `Wait` 之前调用”，本质也是内存模型要求：`Wait` 之前没有 `Add`，就没有 happens-before 关系可用。

**数据竞争（data race）** 的定义是：对同一内存位置的写，与另一个读或写**并发**发生，其中至少一方是非原子访问，且两者之间**没有** happens-before 关系。

关于它的后果，需要澄清一个常见说法：Go 里的数据竞争**并不等于** C/C++ 那种“完全未定义、编译器可以做任何事”。语言规范对含竞争的程序仍施加了约束，最核心的一条是：对**单字长或小于字长**的内存位置，每个读必须观察到某次真实发生过的写（可能是并发 goroutine 写的），而不是一个凭空捏造的值。`go build -race` 检测到竞争时报告并终止进程，也是规范允许的反应之一。

但这**绝不**意味着“竞争最坏也就是读到旧值”这种温和后果可以接受：

- 上述保证只管**字长以内**的位置。数组、结构体、复数这类较大的对象，一次读可能被实现为多次子读，竞争下会出现**撕裂（torn read）**——拿到一半新、一半旧的组合值。
- 编译器优化、寄存器缓存、指令重排都可能让结果超出直觉；没有 happens-before，编译器完全可以把你认为“一定顺序发生”的两件事重排。
- 规范明确把竞争定性为错误。

唯一的正确做法是**消除竞争**——用 `38-并发基础.md` 的“数据竞争与死锁”一节里说的 mutex、`sync/atomic` 或 channel 保护所有共享数据访问。

实践上：写并发代码时先问“这个共享变量的读和写之间，靠什么建立 happens-before？”，答不上来就是 bug。然后用 `go test -race ./...` 验证——race detector 只在**真正执行到**竞争路径时才报告，所以覆盖不到的路径它也不会替你发现。
