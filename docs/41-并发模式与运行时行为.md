## 并发模式

### worker pool

```go
jobs := make(chan int)
results := make(chan int)

var wg sync.WaitGroup

for i := 0; i < 3; i++ {
    wg.Add(1)

    go func() {
        defer wg.Done()

        for job := range jobs {
            results <- job * 2
        }
    }()
}

go func() {
    for i := 1; i <= 5; i++ {
        jobs <- i
    }
    close(jobs)
}()

go func() {
    wg.Wait()
    close(results)
}()

for result := range results {
    fmt.Println(result) // 2 4 6 8 10 各打印一次，但顺序不固定：三个 worker 在并发处理
}
```

### fan-in

多个输入 channel 合并到一个输出 channel：

```go
func merge(chs ...<-chan int) <-chan int {
    out := make(chan int)

    var wg sync.WaitGroup

    for _, ch := range chs {
        wg.Add(1)

        go func(ch <-chan int) {
            defer wg.Done()

            for v := range ch {
                out <- v
            }
        }(ch)
    }

    go func() {
        wg.Wait()
        close(out)
    }()

    return out
}
```

### pipeline

每个 stage 从上游读取，处理后写入下游：

```go
func generate(nums ...int) <-chan int {
    out := make(chan int)

    go func() {
        defer close(out)

        for _, n := range nums {
            out <- n
        }
    }()

    return out
}

func square(in <-chan int) <-chan int {
    out := make(chan int)

    go func() {
        defer close(out)

        for v := range in {
            out <- v * v
        }
    }()

    return out
}
```

### 信号量

用带缓冲 channel 限制并发数：

```go
sem := make(chan struct{}, 3)
results := make(chan int, 10)

var wg sync.WaitGroup

for i := 1; i <= 10; i++ {
    sem <- struct{}{} // 取令牌：满了就在这里等

    wg.Go(func() {
        defer func() { <-sem }() // 还令牌

        results <- i // 谁先拿到令牌谁先做，所以写进结果的顺序不确定
    })
}

// 必须等所有任务真的结束：主 goroutine 先退出的话，只会打印出结果的一部分
wg.Wait()
close(results)

sum := 0
for v := range results {
    sum += v
}

fmt.Println(sum) // 55 —— 顺序不确定，但 1..10 一个不少
```

## goroutine 泄漏

goroutine 启动后如果永远阻塞，就会泄漏。

```go
func leak() {
    ch := make(chan int)

    go func() {
        ch <- 1
    }()
}
```

这个 goroutine 可能永远等不到接收者。使用 context、超时和 `select` 可以避免泄漏。

### 检测泄漏

数量层面用 `runtime.NumGoroutine()`，它返回当前存在的 goroutine 数：

```go
before := runtime.NumGoroutine()

// ... 跑一段会启动 goroutine 的代码 ...

// 等被测代码真正结束要用同步原语（WaitGroup / channel）或轮询到数量稳定，
// 不要靠 time.Sleep 猜时间——本篇结尾“并发设计建议”里也强调过这点

fmt.Println(before, runtime.NumGoroutine())
```

用它做测试断言时注意两点：这个数**包含运行时自己的 goroutine**（GC、finalizer 等），所以不要写死等于某个常数，而应该比较“运行前后有没有增长”；另外刚 `close` 掉 channel 的 goroutine 不会立刻消失，需要给它一点时间或者用同步原语确认。

`NumGoroutine` 只给数量，定位不到是**谁**泄漏了。看调用栈用 `runtime/pprof`：

```go
prof := pprof.Lookup("goroutine")

fmt.Println(prof.Name(), prof.Count()) // goroutine <当前 goroutine 数>

// 2 表示带完整调用栈
if err := prof.WriteTo(os.Stdout, 2); err != nil {
    fmt.Println(err)
    return
}
```

`pprof.Lookup` 返回 `*pprof.Profile`（名字不存在时返回 `nil`），`WriteTo(w, 2)` 会打印所有 goroutine 的调用栈，一眼就能看出它们卡在哪一行、在等哪个 channel。线上排查更方便的是把 profile 挂到 HTTP 端点上用 `curl` 抓——挂载方式和端口注意事项见 `34-runtime与性能剖析.md`。

本版本的 `runtime/pprof` 还预定义了一个 `goroutineleak` profile（`pprof.Lookup("goroutineleak")`），由运行时在 GC 时标记那些**被判定为永久阻塞且已经不可达**的 goroutine。不过它的判定有前提条件，`Count()` 返回 0 **不能**说明没有泄漏——实际定位问题仍然以 `goroutine` profile 的完整栈为准，`goroutineleak` 只是一个辅助提示。

**把这两者当常规工具用**：写任何会启动 goroutine 的库代码时，配套提供一个 `Close()` / `Stop()` 方法，并在测试里断言“反复创建销毁 1000 次之后 `NumGoroutine()` 没有增长”。goroutine 泄漏在压测时才会暴露成内存和调度开销的持续增长，那时已经很难定位了。

## GOMAXPROCS

**这一节主要面向容器部署**，本地开发或裸机部署大致可以跳过，只要记住默认值够用、不要写死就行。

`GOMAXPROCS` 控制同时执行 Go 代码的操作系统线程数量：

```go
fmt.Println(runtime.GOMAXPROCS(0)) // 随机器与容器 CPU 限额变化，不能写死
```

```go
runtime.GOMAXPROCS(4)
```

Go 1.25 起提供 `runtime.SetDefaultGOMAXPROCS`，它把 `GOMAXPROCS` **恢复成运行时的默认值**（`runtime.GOMAXPROCS(n)` 设过的值不算默认值），并重新开启自动更新。

### 默认值：Go 1.25 起会考虑容器 CPU 限额

**Go 1.25 之前**：默认 `GOMAXPROCS` 基本就是 `runtime.NumCPU()`，也就是**宿主机**的逻辑核数。在一台 64 核机器上被限制到 2 个 CPU 的容器里，程序照样会按 64 个 P 来调度——P 多了会带来额外的调度、GC 和工作窃取开销，和 2 核的 CPU 配额完全不匹配。

**Go 1.25 起**：默认值取以下三者的**最小值**：

- 逻辑 CPU 数（`runtime.NumCPU()`）；
- 进程的 CPU affinity mask；
- **Linux 上 cgroup 的 CPU quota**（cgroup v2 的 `cpu.max`；cgroup v1 对应 `cpu.cfs_quota_us` / `cpu.cfs_period_us`）。

也就是容器里通常说的 “CPU limit” 那一项（注意不是 “CPU request”）。几个细节：

- quota 不是整数时**向上取整**；
- 除非逻辑 CPU 数或 affinity 数本身就小于 2，否则不会把 `GOMAXPROCS` 设到 2 以下；
- 该行为**只影响 Linux**；
- 运行时还会**周期性自动更新**默认值（大约每秒最多一次，程序空闲时更少），以跟上 affinity 或 cgroup quota 的变化。

用 `GOMAXPROCS` 环境变量或调用 `runtime.GOMAXPROCS(n)` 显式设过值之后，自动更新就被关闭；`runtime.SetDefaultGOMAXPROCS()` 可以把默认值和自动更新一起恢复：

```go
fmt.Println(runtime.NumCPU(), runtime.GOMAXPROCS(0)) // 都等于当前可用 CPU 数（本机核数与容器限额的较小值）

runtime.GOMAXPROCS(4)          // 手动固定为 4，自动更新被关闭

runtime.SetDefaultGOMAXPROCS() // 恢复默认值与自动更新
fmt.Println(runtime.GOMAXPROCS(0)) // 回到运行时算出来的默认值
```

两个相关的 GODEBUG 开关（都由 Go 1.25 引入，默认值为 1）：

```bash
GODEBUG=containermaxprocs=0 ./app   # 不考虑 cgroup CPU 限额，退回 NumCPU
GODEBUG=updatemaxprocs=0 ./app      # 关闭周期性自动更新
```

`GODEBUG=containermaxprocs=0` 是最常用的回退手段：如果发现某个服务在容器里升级到 Go 1.25 之后吞吐下降、GC 频率变化，或者你本来就希望它按整机核数跑满（例如做了 CPU pinning 的平台），就加上这个开关。注意 Go 1.25 之前的行为等价于 `containermaxprocs=0`，所以 `go.mod` 里的语言版本如果低于 1.25，这两个开关会默认取 0（GODEBUG 的语言版本兼容规则），升级 `go` 指令本身就是一次行为切换。

排查 CPU 打不满/打太满时，第一件事就是把这两个数都打出来：

```go
fmt.Println("NumCPU:", runtime.NumCPU(), "GOMAXPROCS:", runtime.GOMAXPROCS(0))
```

读法很直接：

- `GOMAXPROCS` **小于** `NumCPU`：正常，这正是 cgroup CPU limit 生效的结果（或者有人设过 `GOMAXPROCS`）。
- `GOMAXPROCS` **等于** `NumCPU`，但你期望它是容器的 limit：检查 `containermaxprocs` 是否被关掉、`GOMAXPROCS` 环境变量是否被设过、以及容器是否真的配置了 CPU quota（只设 “CPU request” 不会产生 quota，因此也不会有上限）。
- 两个值都远小于宿主机核数：那是 affinity mask 在起作用。

## 确定性并发测试：testing/synctest

`testing/synctest` 从 Go 1.25 起进入标准库，用来**不真的 sleep** 地测试基于时间的并发代码。它把一个函数放进独立的 “bubble”，bubble 内部的 `time` 包使用**假时钟**（初始时间固定为 2000-01-01 UTC 午夜）。

```go
func TestTimeout(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        start := time.Now()

        ch := make(chan int)
        go func() {
            select {
            case v := <-ch:
                t.Log("received", v)
            case <-time.After(5 * time.Second):
                t.Log("timeout after", time.Since(start)) // 一定是 5s
            }
        }()

        synctest.Wait()                 // 等 bubble 内所有 goroutine 阻塞
        synctest.Sleep(5 * time.Second) // 假时钟直接推进，真实耗时接近 0
    })
}
```

把上面这段存成 `syn_test.go` 后跑 `go test -v -count=1 ./...`，输出形如：

```text
=== RUN   TestTimeout
    syn_test.go:19: timeout after 5s
--- PASS: TestTimeout (0.00s)
PASS
ok  	sdemo	0.00xs
```

注意日志里的 `time.Since(start)` 是 **5s**，而整个测试的墙钟耗时只有毫秒以下（上面那行 `0.00xs` 里的数字每次都会变，量级不变），因为那 5 秒是 `synctest.Sleep` 把假时钟直接推进的，真实时间没有流逝。

`context.WithTimeout` 同理：在 bubble 里 `synctest.Sleep(timeout)` 之后 `ctx.Err()` 必然等于 `context.DeadlineExceeded`。

三个 API：

- `synctest.Test(t, f)`：在一个新 bubble 中执行 `f`，返回前会等 bubble 内所有 goroutine 退出；bubble 内发生死锁则测试失败。传进去的 `*testing.T` 上**不能**调用 `t.Run`、`t.Parallel`、`t.Deadline`。
- `synctest.Wait()`：阻塞到**当前 bubble 内除自己以外**的所有 goroutine 都进入 durably blocked 状态。用来确定“后台处理已经跑完、停在某个等待点上了”。
- `synctest.Sleep(d)`（**Go 1.27 新增**）：等价于 `time.Sleep(d)` 紧跟一个 `synctest.Wait()`。它比单独调 `time.Sleep` 更可取——如果测试和被测代码 sleep 完全相同的时长，两者谁先被调度是不确定的；`synctest.Sleep` 保证被测代码先“跑稳”再往下走。

“durably blocked”是个严格定义：只有 **bubble 内创建的 channel** 上的阻塞收发、所有 case 都在 bubble 内的阻塞 `select`、`sync.Cond.Wait`、在 bubble 内 `Add` 过的 `WaitGroup.Wait`、以及 `time.Sleep` 才算。**加锁、网络 I/O、系统调用都不算**，因为它们可能被 bubble 之外的事件唤醒。所以 synctest 里不能用 loopback 网络，要用 `net.Pipe()` 之类的假连接。

这就是测试 `time.After` / `time.Ticker` / context 超时逻辑的可靠做法：既不用真的等 5 秒，也不会因为 CI 机器卡顿而 flaky（真实 sleep + 时间断言是最经典的 flaky 来源）。把 `go test -race` 和 synctest 结合起来，时间相关的并发逻辑才算被真正验证过。

## 并发设计建议

- 优先使用 channel 传递数据，而不是共享内存。
- 必须共享内存时使用 mutex 或 atomic。
- 发送方关闭 channel。
- 每个 goroutine 都要有明确的退出路径。
- 使用 context 控制取消和超时。
- 不要用 `time.Sleep` 协调并发逻辑；测试时间相关逻辑用 `testing/synctest`。
- 想清楚每个共享变量的读写在靠什么建立 happens-before。
- 部署到容器时确认 `GOMAXPROCS` 是否符合预期（Go 1.25 起默认考虑 cgroup CPU 限额）。
- 先用简单同步方式写正确，再考虑优化。
- 并发代码要用 race detector 验证。
