# 05 错误处理

> Go 版本：>= 1.27.1  
> 相关标准库：errors、fmt、os

错误处理在 Go 里不是语法结构，而是**约定加标准库**：`error` 是一个内建接口，配套工具都在 `errors` 包里。

设计上的取舍很明确：Go 没有异常，错误是**普通返回值**，所以调用方必须显式判断——`if err != nil` 的重复是显式控制流的代价，换来的是"哪个调用会失败"在代码里一眼可见。`error` 又只是一个接口，所以包作者可以用**方法集**描述"调用方需要知道什么"，而不必暴露具体类型。

错误还是**签名的一部分**：每个可能失败的点都摆在调用处，想无视它必须刻意——把调用直接当语句、或者赋给 `_`。这正是 `if err != nil` 值得重复的原因：它把"可能失败"写在读代码的人一定会看到的地方。

## error 与 errors 包

`error` 是 Go 内置的接口类型（接口本身的语法见 `12-接口.md` 的“接口定义”一节）：

```go
type error interface {
    Error() string
}
```

任何实现了 `Error() string` 的类型都可以作为错误使用。函数通常把 `error` 作为最后一个返回值，而调用方必须先看 `err`、再决定要不要用返回值：

```go
func readConfig(path string) ([]byte, error) {
    data, err := os.ReadFile(path)
    if err != nil {
        return nil, err
    }
    return data, nil
}

// 空路径在所有平台上都打不开，所以输出是确定的
data, err := readConfig("")
if err != nil {
    fmt.Println(len(data), err != nil) // 0 true —— 出错时 data 是零值，不能直接用
    return
}

fmt.Println(len(data)) // 不会走到这里
```

## 创建错误

`errors.New` 创建一个只有文案的错误：

```go
var ErrNotFound = errors.New("not found")

fmt.Println(ErrNotFound)                            // not found
fmt.Println(ErrNotFound == errors.New("not found")) // false —— 每次 errors.New 都是一个新值
```

更常用的是 `fmt.Errorf` 带上上下文，`%w` 会包装原始错误，调用方可以通过 `errors.Is` 或 `errors.AsType` 继续检查——同一个 `readConfig` 改成这样：

```go
func readConfig(path string) ([]byte, error) {
    data, err := os.ReadFile(path)
    if err != nil {
        return nil, fmt.Errorf("read config: %w", err)
    }
    return data, nil
}
```

### 哨兵错误

包级别预定义的错误通常叫哨兵错误：

```go
var ErrNotFound = errors.New("not found")

func find(id int) (string, error) {
    if id <= 0 {
        return "", ErrNotFound
    }
    return "found", nil
}
```

调用方使用 `errors.Is` 判断：

```go
value, err := find(0)

if errors.Is(err, ErrNotFound) {
    fmt.Println("no such id, using default") // 调用方自己的处理
} else if err != nil {
    fmt.Println("unexpected:", err)
} else {
    fmt.Println(value)
}
```

这一支打印的是**调用方自己的处理**，不是错误的文案。`errors.Is` 比的是**值**（`ErrNotFound` 这个变量本身），不是错误信息里的字符串——文案相同并不等于相等：

```go
var ErrNotFound = errors.New("not found")

// 文案一样，但不是同一个值
fmt.Println(errors.Is(ErrNotFound, errors.New("not found"))) // false
```

哨兵错误的用法就这么简单，代价却在**导出即承诺**：调用方写下 `errors.Is(err, ErrNotFound)` 的那一刻，就等于你承诺了这个值永远存在、永远是这个语义；以后想合并错误、换实现，都是破坏性变更（同一条道理见 `18-包与工程组织.md` 的"导出即承诺"）。所以哨兵适合"只有一种失败原因、也不需要携带额外信息"的场景，标准库的 `io.EOF`、`fs.ErrNotExist` 都是这一类。

错误的设计空间其实是三选一，先问"调用方到底需要知道什么"：

| 形式       | 承诺的是什么             | 适用场景                                |
| ---------- | ------------------------ | --------------------------------------- |
| 哨兵错误   | **身份**：就是这个值     | 失败原因单一、无需附加数据              |
| 能力接口   | **性质**：支持这个查询   | 来源多样，只关心“是不是超时”这类性质    |
| 自定义类型 | **数据**：能取出这些字段 | 需要携带上下文，用 `errors.AsType` 提取 |

三者的用法在下面各有小节。

## 错误包装与解包

包装错误可以保留调用链信息：

```go
func load(path string) error {
    _, err := os.ReadFile(path)
    if err != nil {
        return fmt.Errorf("load config: %w", err)
    }
    return nil
}
```

`errors.Is` 会沿着包装链查找目标错误：

```go
_, err := os.ReadFile("")

fmt.Println(errors.Is(err, os.ErrNotExist)) // true
```

但 `%w` 不只是"加一层上下文"，它是**对外承诺**：调用方看到被包装的错误，就会放心地写下上面这段代码去检查内部实现。以后你把 `os.ReadFile` 换成别的实现、不再产生这个错误，调用方就碎了。所以只在确实希望调用方检查时才用 `%w`；**只想加日志上下文、不想让调用方依赖内部实现时用 `%v`**（`fmt.Errorf` 的文档原话：The `%w` verb is otherwise a synonym for `%v`，差别只在能否被 `errors.Is`/`As` 穿透）：

```go
return fmt.Errorf("load config %s: %v", path, err) // 调用方无法穿透，内部实现可以自由更换
```

### 提取具体类型

同一个提取任务，两种写法：

```go
_, err := os.ReadFile("")

// AsType：目标写在方括号里，直接返回（值, 是否命中）
if pathErr, ok := errors.AsType[*os.PathError](err); ok {
    fmt.Println(errors.Is(pathErr.Err, fs.ErrNotExist)) // true
}

// As：结果写进第二个参数
var pathErr2 *os.PathError
fmt.Println(errors.As(err, &pathErr2))               // true
fmt.Println(errors.Is(pathErr2.Err, fs.ErrNotExist)) // true
```

`errors.AsType`（Go 1.26 起；更早的工具链只能用 `errors.As`）省掉中间变量和取地址。`errors.As` 的第二个参数必须是非 nil 指针，指向一个接口类型、或指向实现了 `error` 的类型，不满足会直接 panic（`go doc errors.As` 原话：As panics if target is not a non-nil pointer to either a type that implements error, or to any interface type）。

两者都在包装链上找**第一个**匹配项。`go fix` 的 `errorsastype` 重写器可以把老写法自动改成 `AsType`（用法见 `00-工具链.md`）。

### 目标类型写成接口：用方法集描述能力

这一节用到接口与方法集，语法分别见 `12-接口.md` 的“接口定义”一节和 `11-方法.md` 的“方法集”一节。

目标不必是**具体**的错误类型，也可以是一个**只描述能力**的接口——只要能表达"我需要这个错误支持什么操作"就够了：

```go
type timeoutErr struct{}

func (timeoutErr) Error() string { return "timeout" }
func (timeoutErr) Timeout() bool { return true }

type timeoutError interface {
    error
    Timeout() bool
}

func do() error { return fmt.Errorf("do: %w", timeoutErr{}) }

err := do() // 只调一次：错误可能带状态，调两次未必拿到同一个

if te, ok := errors.AsType[timeoutError](err); ok {
    fmt.Println(te.Timeout()) // true
}

var te interface{ Timeout() bool } // 纯能力接口当不了类型参数，只能交给 As

if errors.As(err, &te) {
    fmt.Println(te.Timeout()) // true
}
```

`errors.AsType` 的类型参数有 `error` 约束（签名就是 `errors.AsType[E error](err error) (E, bool)`），所以目标接口必须内嵌 `error`。不带 `Error()` 方法的纯能力接口写进去会直接编译失败：

```text
interface{Timeout() bool} does not satisfy error (missing method Error)
```

`errors.As` 没这个限制——纯能力接口能用，是因为它**本身是接口类型**，不是因为它实现了 `error`。选择标准就两条：

- 目标是具体类型、或内嵌了 `error` 的接口：用 `errors.AsType`；
- 目标是纯能力接口、或者要兼容 Go 1.26 之前的工具链：用 `errors.As`。

`errors.As` 未命中时**不会**清空目标变量（`AsType` 返回的是零值），所以"复用变量"不是选它的理由：在循环里复用同一个目标变量，未命中时会读到上一轮的旧值。

上面两个方法用的是**值接收者**，所以 `timeoutErr{}` 和 `&timeoutErr{}` 都实现这两个接口。换成指针接收者，值就不再实现 `error`：

```go
type timeoutErrPtr struct{}

func (*timeoutErrPtr) Error() string { return "timeout" } // 接收者是指针
func (*timeoutErrPtr) Timeout() bool { return true }

func doPtr() error { return fmt.Errorf("do: %w", &timeoutErrPtr{}) } // 必须取地址
```

忘了取地址的话，`fmt.Errorf("do: %w", timeoutErrPtr{})` 能编译、能运行，但包装是坏的（打印 `do: %!w(main.timeoutErrPtr={})`，`AsType` 返回 `false`），只有 `go vet` 会拦（`fmt.Errorf format %w has arg timeoutErrPtr{} of wrong type`）；值当 `error` 直接用的地方则是编译期报错：

```text
cannot use timeoutErrPtr{} (value of struct type timeoutErrPtr) as error value in return statement: timeoutErrPtr does not implement error (method Error has pointer receiver)
```

标准库的 `net.Error` 就是这样一种能力接口：它内嵌了 `error`，所以能直接当 `AsType` 的类型参数；除 `error` 本身，网络错误里目前稳定可用的能力只有 `Timeout()`：

```go
type Error interface {
    error
    Timeout() bool

    // Deprecated: Temporary errors are not well-defined.
    // Most "temporary" errors are timeouts, and the few exceptions are surprising.
    // Do not use this method.
    Temporary() bool
}
```

`Temporary()` 已被标准库标记为 deprecated（`go doc net.Error` 原文：Temporary errors are not well-defined... Do not use this method）——"临时性"这个判断在实践里定义不清，大部分情况其实就是超时。自己定义能力接口时同理：**只描述真正稳定的性质**，别把定义模糊的判断暴露成 API。

### 多错误：Join、多个 `%w` 与 Unwrap

两者都是 Go 1.20 起的特性：`errors.Join` 只把多个错误合并起来（它会忽略 `nil`，全是 `nil` 时返回 `nil`），多个 `%w` 在合并的同时还能加上 `fmt.Errorf` 格式串里的统一上下文：

```go
var ErrNotFound = errors.New("not found")

joined := errors.Join(ErrNotFound, os.ErrNotExist)
fmt.Println(errors.Is(joined, ErrNotFound))    // true
fmt.Println(errors.Is(joined, os.ErrNotExist)) // true

multi := fmt.Errorf("load failed: %w; fallback failed: %w", ErrNotFound, os.ErrNotExist)
fmt.Println(multi) // load failed: not found; fallback failed: file does not exist

fmt.Println(errors.Unwrap(joined)) // <nil>
```

它们产生的都是**多错误**：实现的是 `Unwrap() []error`（返回一个切片），`errors.Is`、`errors.As`、`errors.AsType` 会遍历每个分支——`errors.Join` 打印时用换行连接各个错误，多个 `%w` 仍按格式串打印。

`errors.Unwrap` 只认 `Unwrap() error`，对多错误一律返回 `nil`：

```go
wrapped := fmt.Errorf("load: %w", os.ErrNotExist)

inner := errors.Unwrap(wrapped)
fmt.Println(inner == os.ErrNotExist) // true
```

所以判断和提取错误一律用 `errors.Is`、`errors.As` 或 `errors.AsType`。

## 自定义错误类型

需要携带字段时，可以定义自己的错误类型：

```go
type ValidationError struct {
    Field string
}

func (e *ValidationError) Error() string {
    return "invalid field: " + e.Field
}
```

（接收者写在 `func` 和函数名之间的这种写法叫方法，语法见 `11-方法.md` 的“方法声明”一节。）

使用：

```go
return &ValidationError{Field: "name"}
```

调用方可以用 `errors.AsType` 提取：

```go
if validationErr, ok := errors.AsType[*ValidationError](err); ok {
    fmt.Println(validationErr.Field) // name
}
```

## 错误处理风格

前面都在讲"错误长什么样"和"怎么判断、提取错误"，现在来讲"错误怎么处理"。

- 错误应该尽早返回，减少嵌套。
- 只在能够处理错误的地方处理错误。
- 不要忽略 `error`，除非非常确定可以忽略。
- 错误信息通常使用小写，不以标点结尾。它们常被拼进更长的消息里（`log.Printf("Reading %s: %v", filename, err)`），中间冒出一个大写字母或句号会很突兀。
- 包装错误时保留原因，不要丢失原始错误。
- 不要用 `panic` 代替普通的错误返回（它的正当用途见下文“panic 和 recover”一节）。

第一条最值得展开——"尽早返回"的意思是**错误分支先返回，正常路径始终留在最外层**，而不是把正常逻辑套进 `if err == nil` 里（下面两个块里的 `read()`/`validate()`/`save()` 都是省掉实现的占位，只看控制流结构——其中 `save()` 是最后一步，不返回 error）：

```go
// 不好：正常路径被错误分支越推越深，读到 save 时要回溯三层 if
data, err := read()
if err == nil {
    if err = validate(data); err == nil {
        save(data)
    } else {
        return err
    }
} else {
    return err
}

// 好：每个错误就地返回，正常路径读下来是一条直线
data, err := read()
if err != nil {
    return err
}

if err := validate(data); err != nil {
    return err
}

save(data)
```

"不要忽略 `error`"这条也值得展开——所谓"非常确定可以忽略"，指的是**已经没有补救手段**的场景。只读打开属于这一类，写文件完全是另一回事：

```go
// 只读打开：关闭失败也没有补救手段，可以忽略
f, err := os.Open(src)
if err != nil {
    return err
}
defer func() { _ = f.Close() }()

// 写文件：写入和关闭失败都可能意味着数据没写下去，都得让调用方知道
w, err := os.Create(dst)
if err != nil {
    return err
}
if _, err := w.Write(data); err != nil {
    return err
}
return w.Close()
```

写文件的 `Close` 别顺手忽略：最后一次写入失败可能只有它报得出来（`bufio.Writer` 这类带缓冲的还要先 `Flush`，`os.File` 本身没有缓冲）。

## panic 和 recover

`panic` 用于表示程序无法继续执行的异常状态：

```go
panic("something bad")
```

`recover` 可以捕获 `panic`，但只能直接在 `defer` 调用的函数中生效：

```go
func safe() (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("recovered: %v", r)
        }
    }()

    panic("boom")
}
```

`recover` 适合处理极少数必须恢复的场景。普通错误应该通过 `error` 返回，而不是用 `panic` 和 `recover` 代替控制流。

那么什么时候该用 `panic`？三种情况：

- **包级初始化**：`regexp.MustCompile`、`template.Must` 这类 `Must` 包装器——模式或模板写错就该在启动时炸掉，而不是拖到运行期（见 `30-regexp.md` 的“编译与匹配”一节、`37-优先队列与模板.md` 的“text/template”一节）。
- **不该发生的情况**：`switch` 的 `default` 分支、或者所有合法输入都已处理完之后，用 `panic` 表示"这不该发生"。它同时是给后来者的断言：真发生了说明前面的判断有 bug。
- **库的内部实现**：内部深层可以 panic，在包的边界 `recover` 转成 `error` 返回。`encoding/json` 就是这么做的：编码过程内部 panic 一个只有它认识的 `jsonError`，顶层 `recover` 把它转成普通 `error`，**认不出类型就重新 panic**，把真正的 bug 放出去。这是高级技巧，公开 API 不要依赖它，但读源码时会遇到。

### `panic(nil)` 的行为变了（Go 1.21）

这是升级时容易踩到的一处**静默语义变化**。用 `recover` 判断"有没有发生 panic"的代码通常写成 `if r := recover(); r != nil`——在 Go 1.21 之前，`panic(nil)` 会真的让 `recover` 返回 `nil`，于是这段判断**认不出**这次 panic，程序会继续往下跑，把错误状态当成正常状态。

Go 1.21 起，`panic(nil)` 会被替换成一个具体的错误值，`recover` 不再返回 `nil`：

```go
defer func() {
    r := recover()
    fmt.Println(r != nil) // true —— panic(nil) 能被 recover 了
}()

panic(nil)
```

所以：

- `recover() != nil` 这个判断从 Go 1.21 起才真正可靠。
- 默认行为由 `go.mod` 的 `go` 行决定：语言版本低于 1.21 的模块默认还是旧行为，1.21 起默认新行为；要强制旧行为可以设 `GODEBUG=panicnil=1`，但不建议依赖。
- 更稳妥的做法是**根本不用 `panic(nil)`**：要表达"带着信息中止"就传一个具体的值或 error。
