# 00 工具链

> Go 版本：>= 1.27.1  

这一篇是**工具箱**，不是语言课：第一次读可以先跳过去，等开始写代码、需要 `go doc` 查标准库、`go vet` 做静态检查，或者用 `-gcflags`、`-race` 排查问题时再回来查。下面按"日常最常用 → 进阶诊断"的顺序排，跳着看没关系。

## go doc：查标准库

标准库是 Go 最重要的资料。遇到常用功能先查标准库是否已经提供，再考虑第三方依赖——`go doc` 就是查它的入口，比搜索引擎可靠，而且版本一定和你本机一致。

四种常见形式：

```bash
go doc                          # 当前包的文档
go doc <pkg>                    # 某个包，如 go doc strings
go doc <pkg>.<sym>              # 包里的某个符号，如 go doc strings.Cut
go doc <pkg> <sym>              # 等价的两参数写法
go doc <pkg>.<sym>.<method>     # 类型的方法，如 go doc json.Decoder.Decode
```

包路径可以只写后缀，`go doc json` 等价于 `go doc encoding/json`（同名时取字典序在前、层级更浅的那个，例如 `template.new` 落在 `html/template`）。符号名匹配时**小写字母不区分大小写、大写字母必须精确匹配**；因此 `go doc json.decode` 和 `go doc json.Decoder.Decode` 会打印同一份文档。

常用 flag：

- `-all`：打印整个包的完整文档，包括所有导出符号的注释。
- `-src`：直接打印符号的**源码**（含函数体），看实现细节时最有用。查一个函数"到底怎么做的"通常一步到位：

```text
$ go doc -src uuid.New
func New() UUID {
	return NewV4()
}
```

- `-short`：每个符号只显示一行摘要（不能和 `-all` 同时用）。
- `-u`：连未导出符号一起显示。
- `-c`：匹配符号时区分大小写。
- `-cmd`：把 `package main` 当普通包显示（默认会隐去它的导出符号）。
- `-ex`：附带可执行示例。

`go doc` **不认 `.` 和 `...` 这类包通配写法**，包路径必须是完整路径或它的后缀。跨 GOROOT 和 GOPATH 查找时，GOROOT 会被完整扫描一遍。

## go vet：静态检查

`go vet` 检查编译器不会报、但几乎肯定是写错了的构造。内建的分析器里，最常撞上的是 `structtag`——它专门报告不符合 `reflect.StructTag.Get` 约定的结构体标签。

结构体标签的内容**不合法不是编译错误**，编译器完全不检查标签，所以下面这段能正常编译：

```go
type Bad struct {
    Age int "json:age" // 缺少引号
}
```

但 `go vet` 会直接指出来：

```text
$ go vet ./...
main.go:6:2: struct field tag `json:age` not compatible with reflect.StructTag.Get: bad syntax for struct tag value
```

标签的格式约定本身见 `09-struct.md` 的"标签"一节。

除 `structtag` 外，`printf`（格式动词与参数不匹配）、`lostcancel`（拿到 `cancel` 却没调用）、`copylocks`（复制带锁的值）也是日常最容易命中的几项。`go vet` 在 `go test` 时**默认会跑**一部分检查，所以很多问题是在跑测试时先暴露出来的。

## gofmt：格式化

`gofmt` 是 Go 生态里几乎没有争议的一条约定：**代码格式不由人决定，由工具决定**。它按固定规则重排空白、对齐、换行，所以任何 Go 代码库看起来都差不多，代码评审也就不会浪费在格式争论上。

四种常用用法：

```bash
gofmt -l .            # 列出「格式与 gofmt 不一致」的文件，不修改
gofmt -d .            # 打印 diff，不修改（评审前想先看改动时用）
gofmt -w .            # 直接改写文件
gofmt -s -w .         # 额外做简化（例如 s[a:len(s)] → s[a:]）
```

`-l` 是最适合接进 CI 的形态：有输出就说明有人没格式化，直接失败即可。

`gofmt` 只做**格式**，不做语义分析，所以它不会帮你改错代码；但 `-s` 会做一批安全的重写，`-r` 还能按规则做批量替换：

```bash
gofmt -r 'a[b:len(a)] -> a[b:]' -w .
```

日常其实不需要手动跑 `gofmt`：

- `go fmt ./...` 等价于 `gofmt -l -w`，按包路径批量执行（注意它会**直接改写**，没有 `-l` 那种"只检查"的形态）。
- `go vet` **不检查格式**，格式检查是 `gofmt` 的职责，两者不能互相替代。
- 编辑器（VS Code 的 Go 插件、gopls）默认在保存时自动格式化，这是实际项目里的常态。

一条实用建议：**别去手写对齐**。结构体字段、连续赋值的对齐都由 `gofmt` 决定，手写的空格在下次格式化后会被改掉，所以写完直接交给它，不要在评审里纠结列宽。

## go build -gcflags：看编译器决策

**这一节涉及"逃逸分析"，需要先了解指针（`10-指针.md`），初读可以跳过**——平时写代码用不上，等排查性能问题再回来。

`-gcflags` 把参数透传给编译器。两个最常用的开关：

- `-m`：打印优化决策，最主要是**逃逸分析**结果——哪个局部变量被搬到了堆上。
- `-S`：打印生成的汇编。

```text
$ go build -gcflags='-m' ./...
./main.go:11:2: moved to heap: x
```

`-m=2` 更啰嗦，会带上"从哪一步逃出去的"调用链：

```text
$ go build -gcflags='-m=2' ./...
./main.go:10:6: cannot inline heapPtr: marked go:noinline
./main.go:11:2: x escapes to heap in heapPtr:
./main.go:11:2:   flow: ~r0 ← &x:
./main.go:11:2:     from &x (address-of) at ./main.go:12:12
./main.go:11:2:     from return &x (return) at ./main.go:12:5
./main.go:11:2: moved to heap: x
```

`-m=2` 的输出里混着内联决策（`cannot inline ...`）和逃逸说明（`flow:` 那几行，说明"从哪一步逃出去的"），行号列号取决于你文件的实际排版。

用 `-S` 对比两段实现是否编译成同一条指令，是确认"某个优化到底有没有生效"的直接手段：例如 `math/bits` 的 `OnesCount64` 会编译成一条 `POPCNTQ`，而手写的逐位循环不会（见 `25-数学与随机数.md`）。

**上面这两段输出对应什么代码、结论怎么读**，见 `10-指针.md` 的"逃逸分析"一节，那里用一个三函数的例子说明"取了地址不等于逃逸"。

## go test -race 与 go run -race：数据竞争检测

race detector 是编译器插桩实现的动态检测：

```bash
go run -race .
go test -race ./...
```

只要**真的执行到**竞争路径，就会看到 `WARNING: DATA RACE` 加两条相反的调用栈（一条写、一条写），进程以非 0 状态退出。

两个限制：

- 它**只报告真正执行到的竞争**，所以 `-race` 通过不等于没有竞争——覆盖不到的路径它也不会替你发现。
- 需要 cgo 与可用的构建缓存，环境不齐时会以 `[setup failed]` 失败，而不是给你一个"没有竞争"的结论。

竞争的定义、后果与消除办法见 `41-同步原语与内存模型.md` 的"内存模型"一节；`39-并发基础.md` 的"数据竞争与死锁"一节给出了最小的可复现例子。

## go fix：现代化重写器

`go fix` 用一组**重写器（analyzer）**自动把旧写法改写成现代写法，相当于官方维护的"升级脚本"。默认一次跑全部；`-NAME` 只跑指定的一项，`-NAME=false` 表示"除了它都跑"。

```bash
go fix ./...            # 直接改写
go fix -diff ./...      # 只看补丁，不改文件
go fix -reflecttypefor ./...   # 只跑一个重写器
```

`-diff` 是推荐的第一步，输出是标准的 unified diff：

```text
$ go fix -diff ./...
--- ./main.go (old)
+++ ./main.go (new)
@@ -8,12 +8,11 @@
 func main() {
-	for _, x := range strings.Split("a,b", ",") {
+	for x := range strings.SplitSeq("a,b", ",") {
 		fmt.Println(x)
 	}
 
-	var pathErr *os.PathError
-	if errors.As(fmt.Errorf("x: %w", os.ErrNotExist), &pathErr) {
+	if pathErr, ok := errors.AsType[*os.PathError](fmt.Errorf("x: %w", os.ErrNotExist)); ok {
 		fmt.Println(pathErr)
 	}
```

本系列正文里提到的重写器：

| 重写器 | 作用 | 相关篇章 |
| --- | --- | --- |
| `reflecttypefor` | `reflect.TypeOf(x)` → `reflect.TypeFor[T]()`（类型在编译期已知时才改写） | `36-reflect与unsafe.md` |
| `stringsseq` | `range strings.Split(...)` → `range ...SplitSeq(...)` | `20-字符串与字节.md` |
| `errorsastype` | `errors.As` → `errors.AsType[T]` | `05-错误处理.md` |
| `newexpr` | 先复制再取地址的惯用法 → Go 1.26 的 `new(expr)` | `10-指针.md` |
| `embedlit` | 复合字面量里省略冗余的嵌入字段名 | `09-struct.md` |
| `omitzero` | 建议把 `omitempty` 换成 `omitzero` | `26-JSON与序列化.md` |
| `unsafefuncs` | 手写的 `unsafe` 指针算术 → `unsafe.Add` 等函数 | `36-reflect与unsafe.md` |

完整的注册列表用 `go tool fix help` 查看，其中与语言版本演进相关的还有 `any`（`interface{}` → `any`）、`minmax`（if/else → `min`/`max`）、`rangeint`（三句式 for → `range n`）、`forvar`（删除 Go 1.22 之后多余的循环变量重声明）、`slicessort`（`sort.Slice` → `slices.Sort`）、`waitgroupgo`（`wg.Add(1)`+`go`+`Done` → `wg.Go`）、`atomictypes`、`mapsloop`、`stditerators` 等。

两点注意：

- 同一份列表里既有"改进建议"型分析器（可作为修复直接应用），也有"可疑构造"型检查（如 `buildtag`、`plusbuild`、`hostport`）。后者的目的更接近 `go vet`，`go tool fix help` 的说明里指出：对前一种用 `go fix -fixtool=PROGRAM`，对后一种用 `go vet -vettool=PROGRAM`。
- 重写器是启发式的，可能报出非问题，所以改写后要跑测试和 `go vet` 复核，不要无脑提交。

## 语言版本门槛（-lang）

编译器强制的是**语言版本**，不是工具链版本：`go.mod` 里 `go` 指令声明的版本就是 `-lang` 的默认值，用到比它新的语言特性会直接编译失败，把问题挡在编译期而不是留到运行期。

以 `new(expr)`（Go 1.26 引入，见 `10-指针.md`）为例，模块声明的是 `go 1.25` 时：

```text
./main.go:6:7: new(42) requires go1.26 or later (-lang was set to go1.25; check go.mod)
```

报错信息里同时给出了**要求的版本**、**实际生效的 `-lang`** 和**去哪里改**。同一条规则也决定了哪些 `go fix` 重写器会生效——重写器不会建议一个当前 `-lang` 用不了的特性。

顺带一提，`go tool` 下还有两个常用的子命令：`pprof` 回答"时间花在哪个函数上"，`trace` 回答"时间线上发生了什么"。它们属于运行时话题——采集方式、命令行用法、页面上各视图怎么读，都在 `35-runtime与性能剖析.md`，本篇不展开。

## 查看程序的构建信息

想知道一个**已经编译好的二进制**是用哪个 Go 版本、什么 `-ldflags`、哪个 commit 构建的，用它自己的 `runtime/debug.ReadBuildInfo()`：

```go
bi, ok := debug.ReadBuildInfo()

fmt.Println(ok, bi.GoVersion) // true go1.27.1
for _, s := range bi.Settings {
    fmt.Println(s.Key, "=", s.Value) // 例如 vcs.revision、-ldflags、GOOS
}
```

这就是"把版本号编进二进制里"的标准做法，排查线上问题时比问同事快得多。`vcs.revision` 一类的字段需要构建时正好在版本控制工作区里，且没有被 `-buildvcs=false` 关掉。

读取**别人的**二进制（不是当前进程）要用 `debug/buildinfo`：

```go
bi, err := buildinfo.ReadFile("/path/to/some-binary")
if err != nil {
    fmt.Println(err)
    return
}

fmt.Println(bi.GoVersion, bi.Path) // 例如 go1.27.1 example.com/cmd/server
```

两个函数读的是同一份信息，区别只在数据来源：`runtime/debug.ReadBuildInfo` 读当前进程，`debug/buildinfo.Read(io.ReaderAt)` / `ReadFile(name)` 读任意文件。常见用途是"这个二进制到底是不是我要的那次构建"——比 `strings` 一下二进制找 commit 号可靠得多。

## 验证文档里的示例

本仓库的文档示例有**自动校验**，不是靠人肉核对。两个入口，都在仓库根目录执行：

**`examples/`**：把文档里值得验证的核心示例写成 `Example` 函数，末尾用 `// Output:` 写出期望输出，`go test` 会真的执行并逐字比对：

```bash
go test ./...
```

这是最可靠的一种"文档测试"——输出写错会直接测试失败。写法约定见 `examples/README.md`。

**`tools/checkdocs`**：直接在 `docs/` 的 Markdown 上做三件事：

```bash
go run ./tools/checkdocs -dir docs                  # 三项检查
go run ./tools/checkdocs -dir docs -examples=false  # 只查断链和锚点（很快）
```

1. **断链**：正文里引用的 `` `NN-xxx.md` `` 是否真实存在。
2. **锚点**：正文里按小节名做的跳转（形如"见《某某》那一节"）能否对应到真实标题。
3. **示例输出**：把 Go 代码块包成程序跑起来，比对该行注释里写的期望输出。

非 0 退出码表示发现问题，可以直接接进 CI——本仓库的 `.github/workflows/ci.yml` 就是这么用的。装了 `make` 的话，`make verify` 一次跑完上面两件事。

几点使用注意：

- 示例检查只覆盖"打印语句上标了期望输出"的块。依赖前文上下文、无法独立运行的片段会被跳过（它们本来就不是完整程序）。
- 多行输出常被文档压成一行写（`// 0 1 2 3 4`），检查会按空白无关 + 逐 token 的方式比对，既能支持这种写法，又能发现某个值根本不在输出里。
- 需要跑编译，所以要有可用的构建缓存；如果报 `permission denied`，把 `GOCACHE` 指向一个可写目录即可。

**改文档里的示例时，先让 `examples/` 或 `checkdocs` 通过，再把代码抄回文档**——顺序反了就容易留下对不上的输出。
