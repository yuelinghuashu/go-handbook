# 33 进程与信号

> Go 版本：>= 1.27.1  
> 相关标准库：os/exec、os/signal、syscall

本篇讲两件与进程直接相关的事：用 `os/exec` 启动外部程序并取回结果，用 `os/signal` 处理中断信号与优雅退出。前置是错误处理与 `context`（`05-错误处理.md`、`39-context.md`，篇内会指出用到的地方）。另外两个相关主题独立成篇：运行时观测与性能剖析见 `34-runtime与性能剖析.md`，反射与 `unsafe` 见 `35-reflect与unsafe.md`。

## os/exec

`os/exec` 用于执行外部程序。最常见的是 `exec.Command` 加 `Output`：

```go
out, err := exec.Command("echo", "hello").Output()
if err != nil {
    fmt.Println(err)
    return
}

fmt.Printf("%q\n", out) // "hello\n"
```

需要同时拿到标准输出和标准错误时用 `CombinedOutput`：

```go
out, err := exec.Command("git", "status", "--short").CombinedOutput()
if err != nil {
    fmt.Println(err)
    return
}

fmt.Println(string(out)) // 取决于当前目录的 git 状态：干净的仓库是空输出，不在仓库里则 err 非 nil
```

只关心退出状态、输出直接交给终端时用 `Run`，通过 `Stdout`、`Stderr`、`Stdin`、`Dir`、`Env` 控制子进程：

```go
cmd := exec.Command("go", "version")
cmd.Stdout = os.Stdout
cmd.Stderr = os.Stderr
cmd.Dir = "/tmp"
cmd.Env = append(os.Environ(), "GOFLAGS=-mod=mod")

if err := cmd.Run(); err != nil {
    return err
}
```

`Stdout` 和 `Stderr` 可以指向任意 `io.Writer`（例如 `bytes.Buffer`）；为 `nil` 时对应输出会被丢弃，连接到一个空设备。

命令非零退出时返回的是 `*exec.ExitError`，用 `errors.As` 取出退出码：

```go
err := exec.Command("sh", "-c", "exit 3").Run()

var exitErr *exec.ExitError
if errors.As(err, &exitErr) {
    fmt.Println(exitErr.ExitCode()) // 3
}
```

`ExitCode` 来自内嵌的 `*os.ProcessState`。用 `Output` 时如果没有另外设置 `cmd.Stderr`，Go 会把子进程标准错误的一部分填进 `ExitError.Stderr` 方便排查（输出很长时只保留首尾）：

```go
_, err := exec.Command("sh", "-c", "echo boom 1>&2; exit 1").Output()

var exitErr *exec.ExitError
if errors.As(err, &exitErr) {
    fmt.Printf("%s", exitErr.Stderr) // boom
    fmt.Println(exitErr.ExitCode())  // 1
}
```

需要超时或取消时用 `exec.CommandContext`：

```go
ctx, cancel := context.WithTimeout(context.Background(), time.Second)
defer cancel()

out, err := exec.CommandContext(ctx, "sleep", "5").Output()
```

需要边跑边读输出这类长时间运行的进程时，用 `cmd.Start()` 启动、`cmd.Wait()` 回收，两者必须成对出现，只 `Start` 不 `Wait` 会泄漏进程资源。

### exec.Command 不经过 shell

这是最容易误判的一点：`exec.Command` 不启动 shell，它把每个参数逐个作为 `argv` 元素传给新进程，所以 `*`、`|`、`>`、`$VAR` 都不会被解释：

```go
out, _ := exec.Command("echo", "*.go").Output()

fmt.Printf("%q\n", out) // "*.go\n"，没有做通配符展开
```

所以既不要指望 `exec.Command("ls", "*.go")` 会展开通配符（需要时用 `filepath.Glob` 自己展开），也不要指望管道和重定向能用。

反过来说，一旦把命令交给 shell，就必须假设存在注入攻击。**绝不要把不受信任的输入拼进 `sh -c`**：

```go
// 危险：user 传入 "a; rm -rf /" 会被当命令执行
bad := exec.Command("sh", "-c", "echo "+user)

// 正确：常量命令模板 + 用户输入作为独立参数，不经过 shell
good := exec.Command("echo", user)
```

只有当命令模板是常量、变量只作为独立参数传递时，`sh -c` 才是可以接受的。另外 `cmd.String()` 只用于调试打日志，它的输出明确不适合再送进 shell 执行。

## os/signal

信号处理用 `signal.Notify`，接收通道必须是带缓冲的：

```go
ch := make(chan os.Signal, 1)

signal.Notify(ch, os.Interrupt, syscall.SIGTERM)

sig := <-ch
fmt.Println("got:", sig) // terminated（收到 SIGTERM 时）

signal.Stop(ch)
```

`os/signal` 向通道发送信号时不会阻塞：通道满了，信号就被丢弃。所以缓冲至少要能容纳预期的信号量，只监听一个信号时缓冲 1 通常就够；用无缓冲通道或者只注册不读取，都会表现为“程序收不到信号”。

跨平台的信号常量只有 `os.Interrupt`（SIGINT，也就是 Ctrl+C）和 `os.Kill`（SIGKILL），而且 `os.Kill` 和 SIGSTOP 都无法被捕获。其余信号常量都在 `syscall` 包里，属于平台相关 API：`syscall.SIGTERM` 是 Unix 上最常用的优雅退出信号。因为 Windows 上这些常量的取值和投递语义都不一样，用到它们的代码要放进只在 Unix 上编译的文件里，用 `//go:build unix` 这类构建约束控制（写法见 `18-包与工程组织.md` 的"构建约束"一节）。

更现代的做法是用 `signal.NotifyContext` 把信号变成 `context.Context`，和已有的取消逻辑统一：拿到 `ctx` 之后传给 HTTP server、数据库查询等支持 context 的调用，让它们一起退出。`stop` 必须调用——它释放相关资源并恢复该信号的默认行为。服务端优雅关闭的完整写法（含 `Shutdown` 超时）见 `30-网络与HTTP.md`。

```go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()

<-ctx.Done()

fmt.Println(context.Cause(ctx)) // interrupt signal received
```

`signal.Stop(ch)` 之后通道不会再收到信号，`signal.Reset()` 恢复默认行为，`signal.Ignore()` 让信号被忽略。优雅退出时记得给清理逻辑留超时，不要让进程卡在 `Shutdown` 上。
