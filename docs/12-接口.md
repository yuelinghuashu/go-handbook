# 12 接口

> Go 版本：>= 1.27.1  
> 相关标准库：io、io/fs、errors、net/http、encoding/json、encoding/xml、sort

## 接口定义

接口是一组方法签名的集合。只要一个类型实现了接口中的全部方法，它就实现了这个接口。

```go
type Speaker interface {
    Speak() string
}
```

定义一个具体类型：

```go
type User struct {
    Name string
}

func (u User) Speak() string {
    return "hello, " + u.Name
}
```

`User` 实现了 `Speaker`，可以直接赋给接口变量：

```go
var s Speaker = User{Name: "Tom"}

fmt.Println(s.Speak()) // hello, Tom
```

Go 的接口是隐式实现的，不需要 `implements` 关键字。

## 接口变量

接口变量保存两个部分：

- 动态类型
- 动态值

```go
var s Speaker = User{Name: "Tom"}
```

这里 `s` 的动态类型是 `User`，动态值是 `User{Name: "Tom"}`。

调用接口方法时，实际调用的是动态类型的方法：

```go
fmt.Println(s.Speak())
```

接口本身可以调用方法，但不能直接访问动态类型的字段。

```go
// fmt.Println(s.Name) // 非法
```

## 空接口与 any

空接口不包含任何方法，因此所有类型都实现它：

```go
var v interface{}
```

`any` 是 `interface{}` 的别名（别名定义见 `01-变量与基础类型.md` 的“any”一节），下面统一写 `any`。

空接口可以用来保存任意类型的值，但使用前通常需要类型断言或类型 switch。

```go
func print(v any) {
    fmt.Println(v)
}

print(1)
print("hello")
print(true)
```

## 类型断言：把接口值拆回具体类型

类型断言用于从接口值中取出具体类型：

```go
var v any = "hello"

s := v.(string)
fmt.Println(s) // hello
```

如果类型不匹配，直接用这种写法会 panic：

```go
var v any = 42

s := v.(string) // panic
```

安全的形式是使用 comma-ok：

```go
var v any = 42

s, ok := v.(string)

fmt.Println(s)  // 零值
fmt.Println(ok) // false
```

类型匹配时：

```go
v := any("hello")

s, ok := v.(string)
fmt.Println(s, ok) // hello true
```

## 类型 switch

类型 switch 可以根据接口值的动态类型分支：

```go
func describe(v any) {
    switch x := v.(type) {
    case string:
        fmt.Println("string:", x)
    case int:
        fmt.Println("int:", x)
    case bool:
        fmt.Println("bool:", x)
    case nil:
        fmt.Println("nil")
    default:
        fmt.Printf("other: %T", x)
    }
}
```

每个 `case` 中的 `x` 会自动转换成对应类型。

类型 switch 只能用于接口值。

断言试得多了会写成一串 `if`：`v.(string)` 不成立再试 `v.(int)`……类型 switch 就是这件事的语法糖，一眼能看出分支穷举了哪些类型。

## 接口嵌入：把几个接口拼成一个

接口可以嵌入另一个接口：

```go
type Reader interface {
    Read() string
}

type Writer interface {
    Write(s string)
}

type ReadWriter interface {
    Reader
    Writer
}
```

实现 `ReadWriter` 的类型必须同时实现 `Read` 和 `Write`。

## 谁满足接口：方法集判定表

接口是**隐式实现**的——类型定义处不写"我实现了谁"，所以"能不能赋给这个接口"只能由方法集回答：**接口要的每个方法，是否在候选类型的方法集里**（方法集本身的两条规则见 `11-方法.md` 的“方法集”一节）。

| 接口方法写在 | `T` | `*T` | 外层嵌 `T` | 外层嵌 `*T` |
| ------------ | --- | ---- | ---------- | ----------- |
| 值接收者     | ✓   | ✓    | ✓          | ✓           |
| 指针接收者   | ✗   | ✓    | ✗          | ✓           |

每一格都能用编译期断言验：下面这块能编译通过，注释掉的那两行取消注释就会报错。

```go
type Counter int

func (c Counter) Value() int { return int(c) }
func (c *Counter) Inc()      { *c++ }

type Incer interface{ Inc() }

var _ Incer = (*Counter)(nil) // ✓ *Counter 的方法集里有 Inc
// var _ Incer = Counter(0)   // ✗ Counter 不实现 Incer，Inc 的接收者是指针

type Person struct{ Name string }

func (p Person) Hello() string    { return "hello, " + p.Name }
func (p *Person) Rename(n string) { p.Name = n }

type Renamer interface{ Rename(string) }

type OuterV struct{ Person }  // 嵌值
type OuterP struct{ *Person } // 嵌指针

var _ Renamer = &OuterV{} // ✓ 嵌值：外层要取地址，才拿到 *Person 的方法
// var _ Renamer = OuterV{} // ✗ OuterV 不实现 Renamer，Rename 的接收者是指针
var _ Renamer = OuterP{}  // ✓ 嵌指针：值类型也带上了 *Person 的方法
var _ Renamer = &OuterP{} // ✓
```

撞上它时的三种改法：

- **断言写成指针形式**：`var _ Speaker = (*User)(nil)`——值接收者和指针接收者两种情况都成立，也是标准库里最常见的契约写法（见下文“编译期接口断言”一节）。
- **把接口方法统一成值接收者**：只在方法不改接收者时成立；要改状态，就得让调用方拿到指针。
- **嵌入改指针**：`struct{ *Person }` 让值类型也获得指针方法，代价是零值不可用，必须显式初始化。

两个具体报错的原文和读法见下文“编译期接口断言”一节；值调指针方法的调用语法（`c.Inc()` 自动变成 `(&c).Inc()`）见 `11-方法.md` 的“自动取地址与自动解引用”一节。

## 编译期接口断言

不加断言的话，一个类型是否满足某个接口只能靠使用它的地方报错。让编译器替你做这个证明的标准写法（idiom），是在包级别写一个恒为真的变量声明：

```go
type Speaker interface {
    Speak() string
}

type User struct {
    Name string
}

func (u User) Speak() string {
    return "hello, " + u.Name
}

// 断言 *User 实现了 Speaker
var _ Speaker = (*User)(nil)

// 断言 User 实现了 Speaker
var _ Speaker = User{}
```

这里的 `_` 是空白标识符，两行都不会产生真实变量，只是在编译期做一次赋值检查。

写法上的选择：

- 放在包级别，紧跟类型定义或它的方法，而不是放进函数体内，这样每次编译这个包都会检查到。
- 值接收者实现接口时，`(*User)(nil)` 和 `User{}` 都成立。
- 指针接收者实现接口时只能用 `(*User)(nil)`，`User{}` 会失败。

`var _ Speaker = (*User)(nil)` 是最常见的形态，因为它在两种接收者下都适用，标准库和大量项目都用它作为“这个类型必须实现某个接口”的契约声明。

当类型不再满足接口时，报错会直接指向这一行，所以能立刻看出是哪个类型、缺了哪个方法：

```text
cannot use (*User)(nil) (value of type *User) as Speaker value in variable declaration: *User does not implement Speaker (missing method Speak)
```

值形式同理：

```text
cannot use User{} (value of struct type User) as Speaker value in variable declaration: User does not implement Speaker (missing method Speak)
```

方法改为指针接收者后，值形式的断言会给出更具体的原因：

```text
cannot use User{} (value of struct type User) as Speaker value in variable declaration: User does not implement Speaker (method Speak has pointer receiver)
```

这种断言常用于让“某个具体类型必须实现某个接口”成为契约的一部分，例如 `var _ io.Reader = (*MyReader)(nil)`。

## nil 接口陷阱：装了 `nil` 指针的接口不等于 `nil`

走到这里，接口都还挺讲道理；但有一处例外，几乎所有 Go 程序员都栽过一次。

接口值为 `nil` 的条件是动态类型和动态值都为 `nil`。

```go
var s Speaker

fmt.Println(s == nil) // true
```

但把 `nil` 指针赋给接口后，接口并不等于 `nil`：

```go
type MyError struct{}

func (e *MyError) Error() string {
    return "my error"
}

var p *MyError
var err error = p

fmt.Println(err == nil) // false
fmt.Println(err)        // my error
```

原因是接口的动态类型是 `*MyError`，动态值是 `nil`。这种接口值调用方法时可能会导致 panic。返回 `error` 时，不要把未初始化的具体指针直接赋给接口。

## 接口比较：动态类型不可比较时会 panic

接口值可以使用 `==` 和 `!=` 比较。

两个接口值相等，要求动态类型相同，并且动态值相等：

```go
var a any = 1
var b any = 1
var c any = "1"

fmt.Println(a == b) // true
fmt.Println(a == c) // false
```

如果动态类型不可比较，比较接口值会 panic：

```go
var a any = []int{1, 2}
var b any = []int{1, 2}

// fmt.Println(a == b) // panic
```

接口值之间的比较只有在动态类型可比较时才是安全的。动态类型是切片、map 或函数时，比较不是返回 `false`，而是直接在运行期 panic：

```text
panic: runtime error: comparing uncomparable type []int
panic: runtime error: comparing uncomparable type map[string]int
panic: runtime error: comparing uncomparable type func()
```

原因是规范规定两个接口值相等必须同时满足“动态类型相同”和“动态值相等”；动态类型不可比较时无法判断动态值是否相等，只能 panic。同样的规则不仅适用于直接的接口值比较，也适用于比较接口数组，以及含有接口类型字段的结构体。

因此，只要一个接口变量可能持有切片、map 或函数，就不要对它使用 `==`。需要比较时先做类型断言确定动态类型，或者在设计上避免这种比较。

接口值和 `nil` 比较是安全的，因为它只检查动态类型是否为空。

## 常用标准库接口：什么时候该实现哪个

这一节是**索引**，不是教程：每个接口只给签名和"什么时候你会需要它"，用法都在各自的专题篇里。最常打交道的三个先记住——`error`（任何错误值都是它，见 `05-错误处理.md`）、`fmt.Stringer`（想让 `%v` 打印出人话就实现它）、`io.Reader`/`io.Writer`（数据流的通用接口，见 `21-io与流.md`）；其余按需查下面各条。

### fmt.Stringer

实现 `String() string` 后，`fmt` 会优先使用它：

```go
type User struct {
    Name string
}

func (u User) String() string {
    return "User(" + u.Name + ")"
}

fmt.Println(User{Name: "Tom"}) // User(Tom)
```

### error

`error` 是最常用的接口：

```go
type error interface {
    Error() string
}
```

### io.Reader 和 io.Writer

`io.Reader`（`Read(p []byte) (n int, err error)`）和 `io.Writer`（`Write(p []byte) (n int, err error)`）是 I/O 抽象的基础；它们的完整契约、常用实现和配套工具函数见 `21-io与流.md`。

### 其他 io 接口

- `io.Closer`：`Close() error`，关闭资源。
- `io.ReadWriter`：嵌入 `Reader` 和 `Writer`，同时可读可写。
- `io.ReadCloser` / `io.WriteCloser`：分别嵌入 `Reader`+`Closer` 与 `Writer`+`Closer`。
- `io.ByteReader`：`ReadByte() (byte, error)`，逐字节读取；`bufio.Reader` 实现了它。
- `io.ByteWriter`：`WriteByte(c byte) error`，逐字节写入。
- `io.WriterTo`（`WriteTo(w Writer) (n int64, err error)`）与 `io.ReaderFrom`（`ReadFrom(r Reader) (n int64, err error)`）：**可选优化接口**，`io.Copy` 会优先使用它们，从而绕过多余的中间缓冲区。自己实现 Reader/Writer 时，如果能把数据直接搬过去，就顺手实现其中一个。

需要同时读写并关闭时，`io.ReadWriteCloser` 把 `Reader`、`Writer`、`Closer` 三个都嵌入了。

### encoding.TextMarshaler 和 encoding.TextUnmarshaler

- `encoding.TextMarshaler`：`MarshalText() (text []byte, err error)`，把值表示为文本。
- `encoding.TextUnmarshaler`：`UnmarshalText(text []byte) error`，从文本还原值。

`encoding/json` 在类型没有实现 `json.Marshaler` 时会使用 `MarshalText`，并把结果编码成 JSON 字符串；`encoding/xml` 和 `flag.TextVar` 也会用到它们。

### encoding/json.Marshaler 和 encoding/json.Unmarshaler

- `json.Marshaler`：`MarshalJSON() ([]byte, error)`，完全接管自己的 JSON 表示。
- `json.Unmarshaler`：`UnmarshalJSON([]byte) error`，从 JSON 还原。

在 Go 1.27 中，`encoding/json` 的这两个类型是 `encoding/json/v2` 中同名接口的别名。

### http.Handler

`http.Handler` 只有 `ServeHTTP(ResponseWriter, *Request)` 一个方法，实现了它就能注册成 HTTP 处理器。`http.Handle` 直接接收 `Handler`，`http.HandleFunc` 接收普通函数并用 `http.HandlerFunc` 适配成 `Handler`。

### fs.FS

`io/fs.FS` 只有 `Open(name string) (File, error)` 一个方法，是只读文件系统的抽象。`os.DirFS` 把一个目录适配成 `fs.FS`，`embed.FS` 和 `testing/fstest.MapFS` 也实现了它。

### sort.Interface

`sort.Interface` 定义了排序所需的方法，新代码更推荐 `slices.SortFunc`，但标准库中仍有大量接口。

### 只描述能力的接口

上面这些接口都定义了完整的方法集，但接口的另一种常见用法是**只描述一项能力**，让调用方不必知道具体类型。例如"这个错误支持超时判断"可以写成 `interface{ Timeout() bool }`，把它交给 `errors.As` 去包装链上找；标准库的 `net.Error`（其中只有 `Timeout()` 可用，`Temporary()` 已被标记 deprecated）、`io.WriterTo`（`21-io与流.md`）都是这一类的例子。

`errors.As` / `errors.AsType` 在这方面的用法和取舍见 `05-错误处理.md` 的"目标类型写成接口"一节。

## 接口与泛型：同一个写法，两种含义

约束本质上也是接口，区别在于**使用时机**：

- 普通接口是运行期的类型。接口变量保存动态类型和动态值，方法调用在运行期完成动态派发，值是装箱进接口的。
- 作为约束使用时，接口只在编译期描述类型集合，编译器用它检查类型实参，实例化后的代码拿到的是具体类型，没有接口装箱和动态派发。

所以同一个接口写法，用在不同位置含义完全不同：只有方法集合构成的基本接口（basic interface）才能作为普通类型使用，带类型集合的接口（例如 `~int | ~string`）只能当约束。类型集合的完整规则见 `13-泛型与类型系统.md`。

那接口就够了吗？不够——**接口能表达"运行时多态"，却表达不了"对任意类型都成立、而且不装箱"的算法**：`slices.Contains` 为什么能同时处理 `[]int` 和 `[]string`，而且不要求它们实现同一个接口？答案是泛型，接着看 `13-泛型与类型系统.md`。

## 接口设计建议

- 接口尽量小，只包含调用方真正需要的方法。
- 先写具体实现，再根据重复出现的抽象需求提取接口。
- 不要在只有一个实现时过早定义接口。
- 接受接口，返回具体类型，通常能让 API 更灵活。
- 注意指针接收者和值接收者对接口实现的影响。
